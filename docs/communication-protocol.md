# 通信设计概要：雾桌在线虚拟桌游平台

> 文档版本：v0.2（概要设计参考）  
> 状态：用于课程设计规划，尚未实现或进行互操作测试。  
> 使用边界：最终报告只需提取通信方式、主要消息类型和代表性流程；本文件不作为完整 API 规范，不要求在课程设计阶段实现所有接口细节。

## 1. 设计原则

系统中的多个客户端需要通过网络共享房间状态。通信设计应说明请求如何到达负责的服务、操作结果何时可以确认，以及客户端断线或漏收更新后如何恢复。

- 房间管理类操作使用请求—应答方式。
- 实时协作使用双向消息通道。
- 服务端负责验证权限和决定权威结果，客户端不能直接覆盖共享状态。
- 状态变化成功提交后，才向客户端确认成功并传播更新。
- 网络可能延迟、重复或丢失消息，因此不能把“已发送”直接等同于“所有客户端已收到”。

## 2. 通信方式

| 通信方式 | 主要用途 | 设计理由 |
|---|---|---|
| HTTPS/REST | 创建、加入、退出房间，读取房间配置和地图元数据 | 请求—应答语义清晰，适合管理操作 |
| WebSocket | 移动标记、掷骰请求、操作结果和房间实时更新 | 支持客户端与服务端之间持续的双向通信 |
| 持久化状态读取 | 客户端重连后恢复状态 | 不依赖原连接或单次广播一定送达 |

WebSocket 提供实时传输通道，但本身不保证消息已经持久化，也不自动提供断线恢复或“恰好一次”处理。

## 3. 主要消息类别

| 消息类别 | 典型内容 | 处理原则 |
|---|---|---|
| 房间管理请求/响应 | 创建房间、加入房间、查询配置 | 服务端验证身份和访问权限 |
| 实时操作请求 | 移动标记、掷骰、修改迷雾 | 发送操作意图，由服务端验证规则与当前状态 |
| 操作结果 | 成功、冲突、拒绝或可重试错误 | 只有已确认提交的结果才能报告为成功 |
| 房间状态更新 | 已接受的移动、骰子结果、场景变化 | 服务端按接收者权限过滤后发送 |
| 状态重新同步 | 当前房间状态或可用的近期更新 | 重连后重新验证权限；若无法安全补齐，则获取当前授权状态 |

操作标识用于识别同一次逻辑操作。若请求超时，客户端不能仅凭超时断定服务端未提交；安全的重试应复用原操作标识，服务端检查是否已有对应结果，避免重复掷骰等副作用。

## 4. 一次实时操作的流程

~~~mermaid
sequenceDiagram
    participant C as 客户端
    participant G as 接入层
    participant R as 房间服务
    participant D as 持久化存储
    participant O as 其他授权成员

    C->>G: 发送实时操作请求
    G->>R: 转发已认证请求
    R->>R: 检查权限、规则和当前状态
    R->>D: 保存已接受的状态变化和操作结果
    D-->>R: 确认提交
    R-->>G: 返回操作结果
    G-->>C: 返回操作结果
    R-->>O: 发送经过权限过滤的状态更新
~~~

**图 1：实时协作的高层通信流程。** 核心边界是先验证、再提交、后确认和传播。具体消息字段、错误码和重试间隔属于实现阶段的接口规范，不是概要设计必须展开的内容。

## 5. 断线后的状态恢复

客户端重连后，服务端首先重新验证身份和当前房间权限，然后尝试提供可用的近期更新；如果无法确认客户端本地状态完整，或历史更新不可用，就返回当前权限下的完整状态。

~~~mermaid
flowchart TD
    A["客户端重新连接"] --> B["重新验证身份和房间权限"]
    B --> C{"能否安全补齐状态？"}
    C -- "能" --> D["补发可用的近期更新"]
    C -- "不能" --> E["发送当前授权状态"]
    D --> F["恢复实时协作"]
    E --> F
~~~

**图 2：简化的重连恢复流程。** 本设计不规定游标格式、周期对账参数或消息发布器实现。报告只需讲清楚：广播可能丢失，因此恢复必须依赖服务端保留的状态或历史记录。

## 6. 通信故障与安全边界

- **请求超时：** 结果可能尚未提交，也可能已经提交但响应丢失；客户端应查询或使用相同操作标识重试。
- **重复请求：** 服务端应识别同一次逻辑操作，避免重复副作用。
- **实时更新丢失：** 客户端可以重新同步，不把某一次推送当作唯一记录。
- **权限变化：** 服务端在推送和状态恢复时都检查当前权限；战争迷雾隐藏的信息不能出现在未授权消息、快照或错误详情中。
- **服务端故障：** 未确认提交的操作不能被报告为成功；恢复后以持久化状态为准。

## 7. 课程知识点对应

本设计可用于解释 Chapter 4 的请求—应答、消息导向通信、瞬态与持久通信等概念，以及 Chapter 8 中请求超时、重复请求和可靠客户端—服务器通信的故障语义。报告应说明这些概念如何指导选择，而不必把所有候选协议都实现出来。

## 8. 不纳入概要设计的内容

完整 JSON 字段表、REST 路由清单、全部错误码、游标与水位协议、发布器重试参数和连接心跳数值属于实现级接口设计。除非课程要求明确指定，否则最终报告不需要展开这些细节。
