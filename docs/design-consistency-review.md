# 概要设计轻量一致性检查记录

> 审查范围：主规划、概要系统设计、通信设计、技术方案比较、故障场景与图源。  
> 审查方式：检查架构、课程知识点、故障处理和文档之间的概念是否一致；**不开展数据库字段级审查，也不验证代码、性能或故障演练。**  
> 结论：核心架构无需推翻。之前过细的事件游标、周期水位和租约实现方案不作为概要设计基线，报告应回到较高层的设计原则。

## 1. 统一后的概要设计基线

1. **客户端—服务器架构：** 浏览器通过网络访问接入层和房间协作服务。
2. **房间级权威处理：** 同一房间由一个权威处理路径确定有效操作顺序；不同房间可以并行处理。
3. **通信分工：** HTTPS/REST 处理房间管理，WebSocket 处理实时协作。
4. **状态提交与传播：** 服务端验证权限和规则，保存已接受的状态变化后再确认并传播更新。
5. **并发与幂等：** 服务端检查当前状态；操作标识用于识别重试，避免重复副作用。
6. **恢复：** 重连时重新验证权限，补发可用的更新或获取当前授权状态；不把单次广播当作唯一记录。
7. **战争迷雾：** 服务端在实时更新和状态恢复时都执行权限过滤。
8. **故障边界：** 服务进程接管前必须避免旧实例继续写入；数据库复制、自动故障切换和零数据丢失等能力没有实现或测试依据时，不作保证。

## 4. 仍然需要保持一致的表述

- 不把 WebSocket 推送成功等同于数据持久化或所有客户端已收到。
- 不把请求超时等同于服务端未提交。
- 不把客户端本地时间当作同一房间操作顺序的权威依据。
- 不把战争迷雾只当作界面隐藏；服务端推送与状态恢复都必须执行权限检查。
- 不把候选技术写成已经采用或已经验证的机制。
- 不把设计目标写成实测结果，也不承诺没有依据的性能、可用性或零数据丢失。

## 5. Codex 整合前的简化规则

1. 以 docs/plan.md、docs/knowledge-map.md 和本轮精简后的 docs/system-design.md 为主线。
2. 从技术比较与故障场景材料中提炼少量有解释力的内容，不整篇复制。
3. 数据库详细设计和通信接口材料只提供背景，不将字段清单、完整 JSON 或精细协议搬进正文。
4. 正文保留约 5–6 张有独立作用的图，优先选择总体架构、实时操作、并发冲突、重连恢复和权限控制。
5. 保持课程模板章节结构；Chapter 8 容错内容单独成章，模板原总结章节顺延。
6. 原始 raw/ 文件保持不变；本轮不生成最终 Word。
