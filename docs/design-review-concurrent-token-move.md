# 核心场景审查：两名玩家同时移动同一标记

> 用途：用一个简单场景检查需求、架构、通信、同步、一致性和容错之间是否自洽。  
> 深度：概要设计，不定义完整接口字段、数据库锁顺序或事件游标协议。

## 1. 场景

地图上有一个角色标记。玩家 A 和玩家 B 几乎同时尝试移动它。两名玩家的客户端可能显示相同的旧位置，但网络延迟意味着请求不一定同时到达服务端。

## 2. 概要处理

1. 两个客户端分别发送移动意图，而不是直接覆盖整份地图状态。
2. 房间服务验证两人的房间成员身份、操作权限和当前标记状态。
3. 房间服务为同一房间的操作确定处理顺序。先被接受并提交的修改成为新的权威状态。
4. 后到的请求如果仍基于过期状态，服务端拒绝它或要求客户端刷新后重新操作，避免静默覆盖已经提交的结果。
5. 已接受的状态变化保存后，再向有权查看的房间成员发送更新。
6. 如果请求响应丢失，客户端使用原操作标识查询或重试，避免同一次操作被重复执行。

## 3. 时序图

~~~mermaid
sequenceDiagram
    participant A as 玩家 A
    participant B as 玩家 B
    participant R as 房间服务
    participant D as 持久化存储
    participant C as 其他房间成员

    A->>R: 请求移动标记
    B->>R: 请求移动同一标记
    R->>R: 按房间顺序检查当前状态
    R->>D: 保存第一个有效修改
    D-->>R: 确认提交
    R-->>A: 返回权威结果
    R-->>C: 发送权限过滤后的更新
    R-->>B: 若请求基于过期状态，返回冲突/刷新提示
~~~

## 4. 课程知识点

- **Chapter 3 — Processes：** 两个客户端进程可以并发发起操作。
- **Chapter 4 — Communication：** 请求到达时间受网络影响，响应也可能丢失。
- **Chapter 6 — Synchronization：** 房间服务需要为共享状态的修改确定可解释的顺序。
- **Chapter 7 — Consistency and Replication：** 客户端显示可能短暂落后，但不能覆盖服务端已确认的权威状态。
- **Chapter 8 — Fault Tolerance：** 超时后重试必须识别原操作，避免重复副作用。

## 5. 设计边界

本场景不要求每次移动都采用分布式互斥算法，也不要求客户端通过向量时钟合并同一份权威游戏状态。房间服务是操作排序的权威路径；如果未来要允许离线编辑或多主合并，才需要重新评估 CRDT 等更复杂方案。
