# 核心场景设计逻辑审查：两名玩家同时移动同一标记

> 版本：v1.0  
> 状态：概要设计审查素材，不代表功能已经实现或测试。  
> 目标：用一个具体业务场景串起课程 Chapter 1–8 中与分布式系统有关的关键问题，检查需求、架构、通信、同步、一致性和容错之间是否自洽。

## 1. 场景与假设

房间中一个角色标记当前位于地图坐标 \`(4, 5)\`，其对象版本为 \`7\`，房间当前已提交事件序号为 \`107\`。

玩家 A 和玩家 B 都有权限移动这个标记，并且都基于版本 7 的状态发起操作：

- 玩家 A 希望把标记移动到 \`(5, 5)\`。
- 玩家 B 希望把标记移动到 \`(4, 6)\`。

两条请求可能几乎同时到达，也可能因网络延迟而以不同顺序到达服务端。服务端不能依赖客户端的本地时间戳来判断哪个请求“绝对更早”。

本例采用的概要设计假设：

1. 系统采用客户端—服务器架构，由服务端验证权限与规则。
2. 每个房间有一个权威的共享状态修改顺序；不同房间可以并行处理。
3. 每个可变对象有自己的版本号，用来检测客户端基于过期状态发起的修改。
4. 每个房间有一个递增的事件序号，用来排列该房间内已接受的共享状态变化。
5. 状态修改、对应的成功事件和操作结果应有明确且一致的持久化边界；本设计建议在同一数据库事务内提交。
6. 为避免重试产生重复副作用，每次用户操作带有稳定的 operationId；同一次操作的重试复用该 ID。

这些是本项目的设计选择与假设，不应写成课件要求系统必须使用的具体技术。

## 2. 操作如何被处理？

### 第一步：两位玩家读取同一个旧状态

A 和 B 都看到标记版本 7。两人都认为自己正在修改当前状态，这在分布式应用中很常见：客户端屏幕上的状态只是最近一次收到的视图，可能在请求发出前就已经过期。

### 第二步：服务端确定一个权威处理顺序

假设服务端先处理 A 的操作。这里的“先处理”指权威处理路径确定的顺序，不表示系统证明了 A 的用户意图一定比 B 更早。

服务端先验证 A 的身份、成员权限、标记可操作权限和请求参数，再检查 expectedVersion 是否仍为 7。

### 第三步：A 的操作被接受

当前版本确实为 7，因此服务端接受移动，并在一个明确的提交边界内完成以下逻辑结果：

- 标记位置更新为 \`(5, 5)\`；
- 标记版本从 7 变为 8；
- 房间事件序号从 107 推进到 108；
- 记录对应的成功事件与 A 的操作结果。

事务提交后，服务端才能把该操作作为已提交成功的结果返回或发布给其他成员。

### 第四步：B 的旧请求发生版本冲突

服务端随后处理 B 的请求。B 仍提交 expectedVersion = 7，但当前标记版本已经是 8。

服务端拒绝这次过期修改，返回冲突结果和最新版本信息。该请求不能覆盖 A 已提交的位置，也不应作为成功的共享状态事件推进房间序号。系统可以记录这次拒绝的操作结果，以便同一个 operationId 重试时返回相同结果。

这是一种保守的冲突处理策略：它避免静默覆盖，但不自动合并两位玩家的意图。B 刷新状态后，可以根据最新位置重新判断是否发起新的移动；新的用户意图应使用新的 operationId。

## 4. 通信、超时与重复请求

数据库提交和网络响应是两个不同的事件。

例如，A 的移动已经提交，但成功响应在网络中丢失。A 的客户端无法仅凭超时判断操作失败。如果客户端重新发送同一个 operationId，服务端应返回已记录的原结果，而不是再执行一次移动、再次增加版本或产生第二个成功事件。

同样，实时通知也可能重复、延迟、丢失或乱序：

- 收到已经应用过的 sequence，客户端可以识别并忽略重复事件。
- 如果客户端已应用到 107，却先收到 109，说明可能缺少 108；客户端应补发缺失事件，或在必要时请求快照，不能直接宣称同步完成。
- 如果客户端断线，应重新认证并确认当前仍有房间权限，再从 lastSequence 补发事件；若缺失事件已不在保留范围内，则使用与 snapshotSequence 对应的快照，再继续应用后续事件。
- 快照和事件都必须按当前成员权限生成，不能把战争迷雾下的完整内部状态发送给普通玩家。

这里的目标不是承诺网络“恰好投递一次”，而是让已提交的操作可识别、可恢复，并避免重复执行造成额外副作用。

## 5. 两种序号解决不同问题

| 概念 | 作用 | 本例 |
|---|---|---|
| 对象版本 version | 判断特定标记是否被其他操作修改过 | A 将 token.version 从 7 更新为 8；B 的 expectedVersion=7 因过期而冲突 |
| 房间事件序号 sequence | 给房间内已接受的共享状态变化确定顺序 | A 的成功事件是 108；之后其他已接受事件继续使用后续序号 |
| 操作标识 operationId | 识别同一用户操作及其重试 | A 重试仍使用 A1，不能把同一操作当成新操作再次执行 |
| 客户端 lastSequence | 记录客户端已连续应用到的事件位置 | 若客户端只到 107，就需要确认 108 是否已经补齐 |

房间序号应按**整个房间的共享事件流**理解，而不只是单个标记的版本号。比如掷骰结果、场景切换和标记移动都可能属于房间事件流。对象版本则按各个可变对象分别维护。

本例中的房间序号是项目设计的事件排序机制，不能直接称为 Lamport 时钟或向量时钟。逻辑时钟用于理解分布式事件的先后关系；具体共享状态如何被权威接受，仍需要本项目自己的同步规则。

## 7. 设计逻辑审查结果

### 当前逻辑能够闭合的部分

- **需求：** 多名玩家可以同时发起移动，系统必须避免共享状态被静默覆盖。
- **架构：** 服务端作为房间内的权威处理路径，统一校验权限与状态。
- **同步：** 对象版本检测过期修改，房间事件序号排列已接受的变化。
- **通信：** 先明确操作是否提交，再返回结果并传播事件。
- **一致性：** 客户端通过事件序号识别重复或缺失的更新；不同客户端暂时落后是可能的。
- **容错：** 同一操作重试使用相同 operationId；断线后通过事件补发或快照恢复。

### 正文仍需保留的限制

1. 版本冲突策略不自动合并用户意图；刷新后由用户决定是否重新操作。
2. 房间服务如何在多实例部署中确保同一房间只有一个有效权威写入路径，属于总体架构的必要条件；若不展开租约/选举算法，至少要说明这是设计假设和故障恢复边界。
3. 事件日志和快照可支持应用层恢复，但不能替代数据库备份与复制策略，也不能自动保证零数据丢失。
4. 服务端必须在实时事件、事件补发和快照路径都执行权限过滤。
5. 性能目标、恢复时间和数据库高可用方案尚未验证，不能描述成已经实现或测试通过。
