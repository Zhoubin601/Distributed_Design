# 核心场景审查：掷骰成功但响应丢失

> 用途：解释请求超时、幂等重试、持久化和容错之间的关系。  
> 深度：概要设计，不规定完整数据库表结构或消息协议。

## 1. 场景

玩家点击“掷 d20”。服务端已经生成结果并保存，但成功响应在网络中丢失。客户端只看到超时，无法判断服务端到底有没有执行。

如果客户端把超时当作失败并重新掷一次，就可能出现两次不同结果；如果直接显示失败，也可能与房间里其他玩家看到的结果冲突。

## 2. 概要处理

1. 客户端为这次逻辑操作生成一个稳定的 operationId。
2. 服务端检查身份、房间权限和允许的掷骰规则。
3. 服务端执行掷骰，并把结果和对应操作记录一起持久化。
4. 保存成功后，服务端返回结果并向有权限的房间成员传播更新。
5. 如果客户端超时，使用原 operationId 查询或重试。服务端发现该操作已有结果时，返回原结果，而不是再次掷骰。
6. 如果玩家确实想再掷一次，应创建一个新的逻辑操作并使用新的 operationId。

## 3. 时序图

~~~mermaid
sequenceDiagram
    participant C as 玩家客户端
    participant S as 房间服务
    participant D as 持久化存储
    participant O as 其他授权成员

    C->>S: 掷骰请求（operationId=R1）
    S->>S: 验证权限与规则
    S->>D: 保存掷骰结果和操作记录
    D-->>S: 确认提交
    S--xC: 返回成功结果（响应丢失）
    S-->>O: 传播已提交的掷骰结果
    C->>S: 使用 operationId=R1 重试/查询
    S->>D: 查找原操作结果
    D-->>S: 返回已保存的结果
    S-->>C: 返回原结果，不重复掷骰
~~~

## 4. 课程知识点

- **Chapter 1 — Introduction：** 把相关状态和操作结果作为一个事务处理，避免只保存一部分。
- **Chapter 4 — Communication：** 请求超时并不能证明服务端没有执行。
- **Chapter 5 — Naming：** operationId 标识逻辑操作，不是房间地址或随机结果。
- **Chapter 8 — Fault Tolerance：** 重试需要具备幂等语义，避免重复副作用。

## 5. 设计边界

本设计不声称网络消息“恰好投递一次”。目标是让服务端能够识别同一次逻辑操作，并在响应丢失后返回可查询的原结果。网络投递、持久化提交和客户端显示是不同的事情，报告应把它们区分清楚。
