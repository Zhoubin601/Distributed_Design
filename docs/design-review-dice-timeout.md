# 核心场景设计逻辑审查：掷骰结果已提交，但响应丢失

> 版本：v1.0  
> 状态：概要设计审查素材，不代表功能已经实现或测试。  
> 目标：用一次掷骰操作串联客户端—服务器通信、事务提交、命名/操作标识、消息重试与容错恢复。

## 1. 场景与假设

玩家在房间中发起一次 d20 掷骰请求。服务端验证请求后生成结果 \`17\`，将结果和房间事件保存成功；但服务端返回给发起玩家的响应在网络中丢失。玩家只看到请求超时，不知道这次操作是否成功。

如果客户端简单地再发起一次新的掷骰，第二次可能得到另一个结果，例如 \`4\`。此时房间成员可能看到两次掷骰，而发起玩家又不知道哪次结果才对应原始操作。

本例采用以下概要设计假设：

1. 客户端只提交骰子规则与请求参数，不提交最终点数；权威随机结果由服务端生成。
2. 每次逻辑操作带有稳定的 \`operationId\`；同一操作重试时必须复用原 ID。
3. 服务端将已提交的掷骰结果、房间事件序号、事件记录和操作结果放在一个明确的持久化事务边界内。
4. 只有提交成功的结果才能作为已完成操作返回或发布给房间成员。
5. 服务端和客户端都不假定网络消息只会投递一次；重复消息通过操作标识和事件序号识别。
6. 这是一种设计方案，不代表当前仓库项目已实现掷骰功能或已验证随机数质量。

## 2. 正常请求如何处理？

### 第一步：客户端提交操作意图

客户端发送房间标识、稳定的 \`operationId\` 和经过允许的骰子规则参数，例如 d20。身份从已认证连接获取，权限由服务端根据当前房间成员记录判断。

服务端不能信任客户端直接提供的用户身份、角色权限、房间事件序号或最终骰子点数。

### 第二步：服务端检查这是不是一次重试

服务端先检查这个 \`operationId\` 是否已经有持久化的操作结果：

- 如果已有已提交结果，就返回该操作原来的结果，例如 \`17\`，不重新生成随机数。
- 如果该 ID 之前用于不同的请求内容，应拒绝该请求，不能把原 ID 当作另一次新操作。
- 如果没有已提交记录，服务端才继续验证规则、权限并处理这次逻辑操作。

并发重试时也必须依靠持久化的唯一性约束或等效的原子处理，避免两个请求同时把同一操作执行两次。

### 第三步：生成并提交权威结果

服务端按允许的骰子规则生成结果。成功提交的事务需要将以下内容作为同一个逻辑提交单元保存：

- 该操作的最终骰子结果；
- 对应的房间事件及房间序号；
- 该 \`operationId\` 的已完成结果。

如果这些记录分开保存，可能出现“结果已记录但事件不存在”或“事件已发布但结果未可靠保存”等不一致状态。概要设计应先明确提交边界，不必在正文给出 SQL 或锁定顺序。

### 第四步：返回结果并通知房间成员

事务提交成功后，服务端向发起玩家返回 \`17\`，并将已提交的掷骰事件交给通知机制传播给有权限的房间成员。

响应和事件通知是两个不同的通信动作：发给发起者的响应可能丢失，而事件通知可能成功、失败、延迟或重复。因此不能只依赖响应来维持房间历史，也不能把广播成功当作所有成员都已收到的证明。

## 3. 关键故障：响应丢失后的重试

~~~mermaid

    autonumber
    participant C as 玩家客户端
    participant S as 房间服务
    participant D as 持久化存储
    participant P as 事件发布器
    participant R as 房间成员

    C->>S: ROLL_DICE（operationId=R1，规则=d20）
    S->>S: 验证身份、权限与骰子规则
    S->>D: 检查 R1，生成结果并保存结果、事件、操作记录
    D-->>S: 提交成功（结果=17，内部 roomSequence=205）
    S--xC: COMMAND_RESULT（17）响应丢失
    P->>D: 读取已提交且待通知的事件
    D-->>P: 内部掷骰事件 roomSequence=205，结果=17
    P-->>R: 网关扫描后按当前权限投影；客户端事件使用各自连续的 deliverySequence
    Note over C: 客户端超时，不知道操作是否提交
    C->>S: 使用同一个 operationId=R1 重试
    S->>D: 查询已提交的操作结果 R1
    D-->>S: 原结果=17
    S-->>C: 返回原结果 17，不重新掷骰
~~~

**图示边界：** 本例假设事务已经提交，只是响应丢失。若第一次请求在提交前失败，重试时系统仍需要通过同一操作标识和原子提交规则，确定是否存在已提交结果；不能仅凭客户端超时推断提交状态。

## 4. 为什么同一个 operationId 很重要？

\`operationId\` 不是骰子的结果，也不是房间序号。它回答的是：**“这是不是用户之前发起的同一次逻辑操作？”**

假设原请求为 \`operationId=R1\`，参数是 d20：

- 第一次请求提交成功，结果为 17，响应丢失。
- 客户端超时后以 R1 重试，服务端查到已提交结果并返回 17。
- 如果 R1 被重复投递，系统不应产生第二条成功的掷骰事件。
- 如果客户端把 R1 搭配不同骰子规则重新发送，服务端应拒绝该冲突请求，而不是复用旧结果或将其悄悄当成新操作。
- 如果用户确实想再掷一次，那是一个新的逻辑操作，应生成新的 operationId。

这属于应用层的幂等处理。它能避免重试导致重复副作用，但不代表底层网络实现了“恰好一次投递”。

## 5. 通信、持久化和事件传播的边界

| 概念 | 在掷骰场景中的含义 | 不能据此推断什么 |
|---|---|---|
| 请求已发送 | 客户端把请求交给通信层 | 不代表服务端收到或处理了请求 |
| 响应超时 | 客户端在期限内没有收到结果 | 不代表服务端操作失败 |
| 事务已提交 | 权威结果、操作记录和事件按设计边界持久化成功 | 不代表发起者或所有成员都已收到消息 |
| 事件已发布 | 通知机制尝试传播已提交事件 | 不代表每个客户端都收到且应用成功 |
| 使用原 operationId 重试 | 查询或返回原逻辑操作结果 | 不代表所有类型的请求都可以不加区分地重试 |
| 房间事件 sequence | 标识房间共享事件流中的顺序 | 不代表该值是随机结果，也不等同于逻辑时钟 |

若事件通知丢失，系统应能依靠持久事件记录重新通知，或在客户端重连时补发缺失事件。若客户端收到重复事件，可根据房间序号识别；若发现序号缺口，应请求补发或获取适当的快照，而不是静默跳过。

## 7. 设计逻辑审查结果

### 当前逻辑能够闭合的部分

- **业务需求：** 掷骰结果是房间共享的权威事件，不能因重试而悄悄产生多个不同结果。
- **架构：** 服务端负责验证权限、生成权威结果和确定事件顺序。
- **通信：** 客户端使用请求—应答发起操作，事件通知负责把已提交结果传播给其他成员。
- **持久化：** 操作结果与房间事件有明确的提交边界，避免只返回了结果却没有可靠记录。
- **容错：** 响应丢失后以同一个 operationId 重试，服务端返回原结果。
- **一致性：** 房间成员按事件序号应用已提交事件；缺失事件通过补发或恢复流程处理。

### 正文仍需说明的限制

1. 幂等只在操作记录可靠保留且检查/提交过程具备原子性时成立；具体记录保留期是后续设计事项。
2. 服务端随机数生成策略与骰子规则格式尚未最终确定；概要设计只需说明权威结果由服务端生成，不应声称已验证随机性或公平性。
3. 如果数据库提交结果本身处于不确定状态，系统需要查询同一 operationId 的持久化结果或安全重试，不能仅根据连接异常决定重新执行。
4. 持久事件记录可以支撑应用层恢复，但不能替代数据库备份与复制配置，也不能自动保证零数据丢失。
5. 这份场景用于解释设计逻辑；是否需要实际实现和测试幂等流程，应以课程任务的实际要求为准。
