# 故障场景与恢复策略矩阵（v0.1）

> 当前阶段：规划素材，不代表系统已实现或完成故障演练。  
> 目的：把 Chapter 8 的故障模型与项目中的具体恢复行为连接起来。  
> 关联：docs/technology-comparison.md、docs/system-design.md、docs/database-design.md、docs/communication-protocol.md。

## 1. 故障模型边界

当前设计先覆盖常见的非恶意故障：

- 浏览器断线、刷新或短暂离线；
- 网关或房间服务进程崩溃、重启；
- 网络延迟、消息重复、通知丢失或响应超时；
- Redis 暂时不可用；
- PostgreSQL 暂时不可用；
- 协调者租约到期后，旧实例恢复并尝试继续写入；
- 客户端事件序号出现缺口，或本地状态无法验证。

当前不声称覆盖拜占庭容错、恶意服务节点共谋、跨地域灾难恢复或零数据丢失。相关能力需要独立需求、威胁模型和部署设计。

| F-11 | 房间快照与客户端/服务端 schema 版本不兼容 | schemaVersion 不受支持或载荷校验失败 | 使用兼容转换，或要求重新同步/明确报错；不得静默合并未知字段 | 恢复可能延迟；避免错误状态被当作正确状态 | 快照 schemaVersion 与事件序列 | Ch.7 复制/一致性；Ch.8 恢复 |

## 3. 故障处理原则

1. **检测不等于证明。** 心跳或超时只能说明对端可能不可达，不能证明进程已经永久停止。
2. **超时不等于失败。** 服务端可能已提交事务，但响应在网络中丢失。写操作应通过稳定 operationId 查询或重试。
3. **通知不等于持久化。** 实时通知只是传播机制；权威状态与事件的提交边界由数据库事务决定。
4. **重连先鉴权。** 恢复之前必须重新验证当前成员状态和可见权限，不能直接重放历史缓存。
5. **恢复必须有序。** 客户端按 deliverySequence 检查当前授权视图流；内部 roomSequence 会因权限过滤而跳号，不可直接用于缺口判断。周期性水位对账用于发现最后一条通知丢失的情况。
6. **旧协调者必须被隔离。** 如果采用租约和 epoch，每次权威写事务都要校验；只在服务启动时校验不足以防止旧实例恢复后写入。
7. **明确数据持久性边界。** PostgreSQL 备份周期、同步/异步复制、RPO/RTO 尚未确认前，不承诺零数据丢失或固定恢复时间。

## 5. 仍待确认的恢复参数

- 数据库备份周期与恢复演练要求；
- PostgreSQL 是否采用主备复制，若采用则是同步还是异步；
- 可接受的数据丢失窗口（RPO）和恢复时间目标（RTO）；
- 快照生成频率、事件保留期限与清理规则；
- 租约期限、续期周期、故障接管条件和数据库故障时的写入策略；
- 课程设计是否需要实际实现这些故障测试，还是只要求概要设计与测试计划。

这些参数不能仅凭当前资料擅自确定，应在需求确认或部署方案确定后补充。
