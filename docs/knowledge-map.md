# 课程知识点覆盖与写作检查表（v1.0）

> **用途：** 为概要设计报告核对课程 Chapter 1–8 的覆盖情况，防止只介绍功能或只罗列技术名词。  
> **理论主来源：** `raw/Introduction to Distributed System-by JieSong NEU.pdf`，课堂使用的《Introduction to Distributed System》。本文件依据已有课件阅读记录整理，正式写作时应回到 PDF 核对原文、图表与具体术语。  
> **作业依据：** `raw/要求.txt` 要求对指定分布式系统进行概要设计，明确技术需求并运用所学知识，评分关注需求明确、设计完整、设计正确、自主知识运用、选题新颖和格式良好。  
> **设计主线：** 多个浏览器客户端通过网络共同操作同一桌游房间，系统需要处理通信延迟、并发修改、共享状态、命名、部分故障和恢复。  
> **深度边界：** 这是知识覆盖清单，不是最终报告正文，也不是实现任务清单。每章要解释与系统有关的概念并作出设计判断，但不要求把课件中的每个算法都实现。

## 1. 评分点与检查方法

| 评分点 | 报告应当让老师看到什么 | 避免的问题 |
|---|---|---|
| 需求明确 | 系统服务谁、有哪些功能、为何需要分布式设计，以及有哪些网络/故障假设 | 只列桌游功能，却没有分布式技术需求 |
| 设计完整 | Chapter 1–8 均有明确的报告落点；不适用的知识点也说明适用边界 | 只写架构和数据库，遗漏命名、同步、一致性或容错 |
| 设计正确 | 用代表性场景解释请求、共享状态、冲突、消息传播和恢复之间的关系 | 把实时广播等同于可靠保存；把网络超时等同于确定故障 |
| 自主知识运用 | 说明“遇到什么问题、考虑过什么方案、为何选择、代价是什么” | 只抄定义，或为了显示复杂而堆叠算法名称 |
| 选题新颖 | 用多人桌游特有的标记并发移动、战争迷雾和断线续玩等场景分析分布式问题 | 把普通 CRUD 功能换个名字，却没有具体的分布式问题 |
| 格式良好 | 图表与正文互相解释，术语和编号统一，遵循课程模板 | 大量图表重复同一内容，或在正文堆入实现级参数 |

## 3. Chapter 1–8 应用矩阵

每章按四个问题组织：**概念是什么 → 本系统遇到什么问题 → 采用或比较什么方案 → 选择的理由和限制是什么。**

### Chapter 1 — Introduction（PDF 第 1–45 页）

**核心问题：为什么这个桌游平台属于分布式系统？**

- **要解释的课件知识：** 分布式系统的定义与目标；透明性、开放性、可扩展性；分布式环境的挑战与常见陷阱；事务和 ACID。
- **业务映射：** 主持人和玩家运行独立客户端，通过网络共享房间状态。网络可能延迟、中断或重复传递消息；一个客户端或服务节点出现问题，不代表其他节点一定同时失效。
- **设计判断：** 明确系统边界、用户、功能、网络假设和恢复需求。若同一次业务更新的状态与历史记录由同一数据库事务管理，可以用 ACID 解释其事务边界；不要把 ACID 扩大解释为网络消息必达。
- **建议证据：** 系统上下文图、功能/技术需求表、设计假设。
- **写作深度：** 说明分布式需求从哪里来，不需要在本章展开数据库事务的具体 SQL。

### Chapter 2 — Architectures（PDF 第 46–84 页）

**核心问题：系统由哪些部分组成，为什么这样组织？**

- **要解释的课件知识：** 分层、事件驱动等架构风格；集中式、去中心化和混合式架构；客户端—服务器与对等结构。
- **业务映射：** 浏览器负责交互；服务端负责成员权限和共享状态的权威处理；不同房间可以分配给不同服务实例。
- **建议选择：** 采用分层的客户端—服务器架构，并按房间组织权威状态。这里的“每房间一个权威操作顺序”不意味着整个系统只有一台服务器。
- **方案比较：** P2P 可以减少对单一中心的依赖，但在本项目中，权限、战争迷雾、统一操作顺序和恢复来源需要额外协调，因此不作为核心架构。
- **建议证据：** 总体架构图、职责说明、C/S 与 P2P 简洁比较表。
- **写作深度：** 说明逻辑组件的职责与调用关系；不要求把每个逻辑组件部署成独立微服务。

### Chapter 3 — Processes（PDF 第 85–138 页）

**核心问题：不同客户端和服务端进程如何协作？**

- **要解释的课件知识：** 线程与并发、虚拟化、客户端与服务器、代码迁移。
- **业务映射：** 主持人和玩家分别运行浏览器客户端；服务端同时处理多个连接和房间。不同房间可以并行处理，同一房间的共享状态修改仍需要有明确的处理顺序。
- **建议选择：** 客户端负责显示和发送操作意图；服务端负责权限、规则和权威状态校验。客户端可先做非权威的拖动预览，但不能自行决定最终共享结果。
- **方案比较：** 说明代码迁移对当前桌游业务没有明显直接需求，因此不纳入核心设计。若讨论虚拟化，应把它定位为部署/隔离手段，而不是自动保证一致性或容错的机制。
- **建议证据：** 客户端与服务端职责表、简单的进程/房间分配图。
- **写作深度：** 解释进程角色和并发关系；不需要指定线程池大小、线程调度参数或容器编排配置。

### Chapter 4 — Communication（PDF 第 139–208 页）

**核心问题：请求、实时更新与恢复信息如何在网络中传递？**

- **要解释的课件知识：** 协议与通信基础、RPC、面向消息的通信、瞬态/持久通信、面向流的通信、多播通信。
- **业务映射：** 创建/加入房间属于请求—应答交互；标记移动和掷骰结果需要及时通知房间成员；断线后的玩家需要恢复错过的状态。
- **建议选择：** 用请求—应答处理管理操作，用双向实时通信承载持续更新；面向房间成员的广播应受成员权限限制。
- **关键边界：** 瞬时通知适合及时传播，但不能独自承担历史恢复；若消息需要在接收者离线后补回，就必须有持久记录或其他可靠恢复来源。连接建立、发送成功和业务状态持久化是不同概念。
- **建议证据：** 一张标记移动消息时序图，清楚标出请求、服务端处理、状态确认、通知和断线后恢复。
- **写作深度：** 讲清通信类型的职责和失败边界；不必列出完整 JSON 字段、所有错误码或每条 API。

### Chapter 5 — Naming（PDF 第 209–267 页）

**核心问题：系统怎样识别资源，并找到对应的服务？**

- **要解释的课件知识：** 名称、实体、地址与标识符；平面命名、结构化命名、基于属性的命名；课件涉及的转发指针、宿主位置、DHT/Chord 和层次化命名。
- **业务映射：** 用户、房间、地图和标记需要可区分的标识；邀请玩家使用的邀请码是加入凭证，不应和房间的稳定标识或当前网络地址混为一谈。
- **建议选择：** 使用稳定的业务标识标记房间与资源，通过房间目录/服务定位机制找到负责处理该房间的服务。
- **方案比较：** 对 DHT/Chord 等去中心化查找方式说明其可解决的问题与维护成本；当前规模不要求自行实现覆盖网络。基于属性的命名只在确实需要按地图标签等条件搜索资源时讨论。
- **建议证据：** 命名概念表，区分“标识什么”“用什么加入”“去哪里访问”。
- **写作深度：** 用少量具体例子解释命名概念；不需要设计完整的 DHT 路由表或查找算法。

### Chapter 6 — Synchronization（PDF 第 268–335 页）

**核心问题：多个用户同时操作共享状态时，系统如何定义先后并处理冲突？**

- **要解释的课件知识：** 物理时钟同步、Lamport 逻辑时钟、向量时钟、互斥和选举算法。
- **业务映射：** 两名玩家可能同时移动同一个角色标记；客户端时间戳可能不同步，网络消息到达顺序也未必等于用户发起操作的顺序。
- **建议选择：** 由房间的权威处理路径确定被接受操作的顺序，并说明过期修改如何被发现和拒绝。房间序号是本项目的设计选择，不应声称它就是 Lamport 时钟或向量时钟。
- **方案比较：** 解释逻辑时钟如何描述事件关系；再说明在有权威房间协调者的设计下，为什么不一定需要让每个客户端通过分布式互斥算法共同批准每次移动。选举算法只有在设计确实需要节点自行选主时才进一步展开。
- **建议证据：** 两名玩家同时移动同一标记的并发示意图，并标出系统如何接受、排序或拒绝操作。
- **写作深度：** 讲清同步问题、方案与取舍；不要求推导所有互斥算法的消息复杂度或完整选举实现。

### Chapter 7 — Consistency and Replication（PDF 第 336–402 页）

**核心问题：玩家看到的共享状态需要多强的一致性，复制又解决什么问题？**

- **要解释的课件知识：** 复制的可靠性、性能和成本；顺序、因果、最终一致性等模型；客户端中心一致性；副本管理、主动复制和 Quorum。
- **业务映射：** 核心游戏状态需要明确的权威顺序；在线状态等临时信息可以容忍短暂滞后。断线玩家回来后，应能够恢复到可验证的房间状态。
- **建议选择：** 按数据类型说明所需保证，而不是笼统声称整个系统“始终强一致”。说明复制有助于可用性或读性能，但会带来副本同步、故障切换与确认语义方面的代价。
- **方案比较：** 将主备复制和 Quorum 作为候选策略比较。若未定义副本数量、读写条件、故障假设和确认规则，不声称采用 Quorum，也不承诺零数据丢失。
- **建议证据：** 一张数据类别与一致性需求对照表，或一段快照/历史事件帮助断线恢复的说明。
- **写作深度：** 解释模型与适用场景；不需要自行设计一套复制协议或给出未验证的 RPO/RTO 保证。

### Chapter 8 — Fault Tolerance（PDF 第 403–502 页）

**核心问题：客户端、服务或网络出现部分故障时，系统如何继续工作或恢复？**

- **要解释的课件知识：** 故障与可靠性、进程韧性、可靠客户端—服务器通信、可靠组通信、恢复、分布式提交；课件包含 2PC 与 3PC。
- **业务映射：** 客户端断线、请求超时、重复请求、房间服务崩溃、通知丢失等情况可能发生；不同故障影响不同，不能假定整个系统同时成功或同时失败。
- **建议选择：** 说明重连后如何恢复共享状态，以及对可能重试的操作如何避免重复副作用。对于房间服务故障，概要设计只需说明恢复依赖、接管前提和未覆盖的边界，不必在正文规定完整租约续期参数。
- **方案比较：** 只有一次业务操作必须跨多个独立事务参与者原子提交时，才有必要深入讨论 2PC/3PC；如果本设计把相关数据放在同一数据库事务内，就解释为何当前不采用分布式提交。
- **故障范围：** 可以把重点放在网络中断、进程崩溃和存储暂时不可用；若不设计拜占庭容错，明确说明不在本项目保证范围内。
- **建议证据：** 一张断线恢复流程图，正文再挑选 2–3 个代表性故障解释预期行为。
- **写作深度：** 说明故障模型、恢复思路与保证边界；详细测试脚本、重试参数和完整故障切换算法作为辅助素材，不作为概要设计主线。

## 4. 核心设计概念与容易混淆的边界

| 概念 | 在本项目中怎么解释 | 不应混淆成什么 |
|---|---|---|
| 房间权威顺序 | 系统为一个房间内被接受的共享状态修改提供可解释的先后顺序 | 不等于整个系统只能运行一个服务实例 |
| 逻辑时钟 | 描述分布式事件之间的逻辑先后关系；依据课件解释 Lamport/向量时钟 | 不等于物理时间绝对准确，也不自动解决所有业务冲突 |
| 实时通信 | 让在线成员较快地收到更新 | 不等于消息一定送达，更不等于数据已经可靠保存 |
| 持久记录 | 为恢复错过的更新提供依据 | 不等于所有客户端在任意时刻都完全同步 |
| 一致性模型 | 描述不同节点/客户端可以观察到怎样的读写结果与顺序 | 不应把顺序、因果、最终一致性当作同一个概念 |
| 复制 | 维护数据的多个副本，可能改善可靠性或性能 | 不等于自动没有数据丢失，也不等于不需要协调 |
| 故障检测 | 根据超时、心跳或错误推断节点可能不可用 | 超时不是节点永久失效的绝对证明 |
| 2PC/3PC | 面向多个事务参与者的分布式提交问题 | 不等于普通的单数据库事务，也不是任何多组件系统都必须使用 |

## 5. 最终报告最少应呈现的证据

以下是建议的概要设计证据，不要求逐项制作独立的大表或大图。

- [ ] **需求证据：** 系统边界、核心功能、分布式技术需求与基本假设。
- [ ] **架构证据：** 一张总体架构图，解释客户端、服务端和存储等部分的职责。
- [ ] **通信证据：** 一条代表性操作时序，说明请求、状态接受、更新传播和通信失败的边界。
- [ ] **命名证据：** 解释稳定标识、邀请码和网络地址的区别。
- [ ] **同步证据：** 用并发移动的具体例子解释排序和冲突处理。
- [ ] **一致性/复制证据：** 说明核心状态和临时状态的不同需求，并比较适用的复制方案。
- [ ] **容错证据：** 说明断线后的恢复流程，并分析至少两个代表性故障。
- [ ] **课程覆盖证据：** Chapter 1–8 每章都能在正文找到概念应用或有理由的方案比较。
- [ ] **方案取舍证据：** 对重要选择说明需求依据、选择理由与代价。
- [ ] **来源证据：** 正式定义、模型和算法描述回到课堂 PDF 原文核对并按模板引用。

## 6. 写作深度与素材使用规则

- 本文件用于**检查覆盖情况**，不是让最终报告把所有条目逐条复制进去。
- 正文优先解释分布式问题与设计逻辑；功能表和技术表服务于论证，不代替解释。
- 从 `docs/system-design.md`、`docs/database-design.md`、`docs/communication-protocol.md`、`docs/technology-comparison.md` 和 `docs/failure-scenarios.md` 中只提取有助于解释课程知识的内容。

- 课件未明确支持的内容不应伪装成课件原话；必要时明确标为“本项目的设计推导”或“补充方案比较”。
- 最终报告的准确章节编号、图表数量和附录形式，以 `raw/课程设计模板.docx` 为准。
