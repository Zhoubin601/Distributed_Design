## 3. 系统定位与边界

### 3.1 系统定位

设计一个浏览器端轻量级虚拟桌游协作平台。主持人和玩家进入同一房间，共享地图、场景与角色标记，并通过实时事件同步状态。报告聚焦多客户端通信、共享状态并发修改、操作排序、权限控制、数据持久化，以及网络或服务节点故障后的恢复。

### 3.2 用户角色

- **主持人（Host）**：创建房间、选择地图、管理场景与迷雾、放置角色标记、控制房间权限。
- **玩家（Player）**：通过邀请码加入房间、查看获授权的场景、移动有权控制的角色标记、发起掷骰操作。

暂不设计访客、运营后台、复杂战役管理等额外角色。

### 3.3 核心场景

1. 主持人创建房间并选择地图，系统生成房间标识和加入邀请码。
2. 玩家通过邀请码加入，服务端检查成员身份、房间状态和加入权限。
3. 主持人调整地图/迷雾/角色标记，玩家按权限移动角色标记。
4. 玩家发起掷骰操作，由服务端校验并生成结果，结果进入房间事件流与历史记录。
5. 在线客户端接收事件并更新场景；重连客户端通过事件补发或快照恢复。
6. 主持人结束房间，系统按保留策略保存或关闭房间状态。

### 3.4 范围控制

**纳入：**房间创建/加入/退出、主持人与玩家权限、地图与场景、角色标记、迷雾控制、掷骰记录、实时通信、事件排序、状态持久化、断线重连和基础故障恢复。

**暂不纳入：**语音视频、支付、公共地图市场、插件生态、完整规则引擎、跨洲容灾、全网状 P2P Mesh。

### 4.2 非功能需求

| 编号 | 目标 | 暂定设计指标 |
|---|---|---|
| NFR-01 | 规模 | 每个房间最多 8 名同时在线成员，含主持人；待确认。 |
| NFR-02 | 实时性 | 同地域、网络正常时，普通状态操作从服务端接受到其他客户端可见的 P95 延迟目标不超过 300 ms；这是目标，不是已测结果。 |
| NFR-03 | 恢复性 | 网络恢复后，普通规模房间的状态恢复目标暂定 5 秒内；须注明测试条件。 |
| NFR-04 | 一致性 | 同一房间内，服务端接受的共享状态变更具有单调递增的序号，客户端最终收敛到服务端确认状态。 |
| NFR-05 | 持久性 | 服务端按明确的持久化策略处理关键操作，避免“广播成功”被误当作“数据已可靠保存”。 |
| NFR-06 | 安全性 | 使用安全传输；邀请码难以猜测；服务端执行权限检查；日志不记录敏感凭据。 |
| NFR-07 | 可扩展性 | 不同房间可以分配到不同协作节点；单个房间的状态顺序由一个逻辑协调者维护。 |

## 5. 总体设计方向

### 5.1 建议架构

采用**服务端权威的客户端—服务器架构**，结合分层架构与事件驱动通信。为了控制复杂度，初版以模块化应用服务为主，不强行拆分大量微服务。

- 浏览器客户端：绘制地图、展示标记、提交操作、按序处理服务端事件。
- 接入/API 层：HTTPS/WSS 接入、基础限流和请求转发。
- 应用服务：房间管理、成员身份、权限和地图元数据。
- 实时协作服务：管理 WebSocket 连接与房间会话；为每个房间提供逻辑上的单一排序协调者。
- PostgreSQL：保存房间元数据、关键场景状态、操作日志和快照。
- Redis：可选地保存在线状态、临时路由和租约；不能作为唯一的持久化事实来源。
- 对象存储：保存地图图片等静态资源。

### 5.2 核心机制候选

- REST 用于房间管理等请求/响应交互；WebSocket 用于实时事件。
- 每个房间使用单调递增的 `roomSeq` 标记已接受事件的顺序。
- 每个客户端操作带唯一 `operationId`，用于识别重试并避免重复副作用。
- 使用持久化操作日志与定期快照支持重连和崩溃恢复。
- 数据库主备复制作为候选持久化方案；必须解释同步/异步复制、故障切换与确认成功操作的持久性边界。

### 5.3 不采用复杂机制的理由

- **CRDT**：当前共享对象类型和业务规模有限，且房间采用服务端排序；先不采用多副本无中心合并。报告仍需说明 CRDT 适用场景与代价。
- **P2P/WebRTC Mesh**：共享操作需要服务端权限校验、统一排序和持久化；不以 P2P 作为核心状态通道。若课堂课件要求覆盖 P2P/覆盖网络，应在架构对比中分析，而非假装系统已经采用。
- **Kafka/复杂微服务**：初版规模不要求引入重量级消息平台；若用 Redis Pub/Sub 做跨节点通知，必须说明它不是可靠日志，缺失事件应由持久化日志补回。
- **Quorum/多主写入**：初版优先考虑主备复制，避免自建仲裁协议；在一致性与复制章节比较 Quorum 的适用条件。
- **向量时钟**：如果每个房间由一个逻辑协调者给操作分配全序，房间序号已可完成核心排序。Lamport/向量时钟应根据课件内容作理论解释与方案比较，不为了覆盖而硬塞进实现。
- **2PC/3PC**：只有存在需要跨多个独立服务原子提交的业务事务时才有必要重点采用；若系统不引入这类事务，应解释适用条件与不采用理由。
