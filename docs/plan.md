## 2. 设计主线：为什么这是一个分布式系统？

本项目不是单纯介绍一款桌游应用。报告要围绕一个核心问题展开：

**多个位于不同设备、通过网络连接的用户，如何共同操作同一个虚拟桌游房间，并在网络延迟、并发操作和部分节点故障时，仍然得到可解释、可恢复的共享状态？**

具体体现为：

- **多个独立进程：** 主持人和玩家运行各自的浏览器客户端，服务端也由独立进程提供服务。
- **网络通信：** 客户端通过网络提交操作并接收其他成员的更新，消息可能延迟、丢失、重复，连接也可能中断。
- **并发与同步：** 多名玩家可能同时移动角色标记或修改场景，系统需要定义操作顺序和冲突处理规则。
- **共享状态与一致性：** 所有人需要看到符合权限、且顺序明确的房间状态；不同类型的数据可以采用不同的一致性要求。
- **部分故障与恢复：** 一个客户端断线不应让整个房间失效；服务节点或网络出现问题时，系统需要说明哪些状态能恢复、恢复依赖什么。
- **扩展性：** 不同房间可以分配给不同服务实例，而不是让所有房间的操作都经过同一个全局处理点。

因此，本系统建议采用**客户端—服务器架构，并按房间组织协作状态**。每个房间有一个逻辑上的权威操作顺序，但多个房间可以由不同服务实例处理。它仍然是分布式系统，不需要为了“分布式”而强行改成完全去中心化的 P2P 架构。

## 3. 系统范围与功能需求

### 3.1 用户角色

- **主持人（Host）：** 创建房间、选择地图、调整场景与战争迷雾、管理成员权限。
- **玩家（Player）：** 通过邀请码加入房间、查看获授权的场景、移动有权控制的角色标记、发起掷骰操作。

暂不纳入访客角色、语音视频、支付、公共地图市场、复杂战役管理和跨地域灾难恢复。

### 3.2 核心功能

| 编号 | 功能 | 用户能做什么 | 对应的分布式问题 |
|---|---|---|---|
| FR-01 | 房间管理 | 主持人创建房间，玩家加入或退出 | 房间命名、服务定位、成员状态 |
| FR-02 | 地图与场景 | 房间成员查看当前地图，主持人切换场景 | 共享状态分发、静态资源访问 |
| FR-03 | 标记协作 | 获授权的成员创建或移动角色标记 | 并发修改、操作排序、状态同步 |
| FR-04 | 权限与战争迷雾 | 主持人控制可见区域和成员操作权限 | 服务端权威、访问控制、信息隔离 |
| FR-05 | 掷骰与回合 | 玩家请求掷骰或推进回合，房间成员看到结果 | 权威结果、重复请求、事件顺序 |
| FR-06 | 实时更新 | 在线成员及时收到已接受的房间状态变化 | 消息通信、广播、延迟与丢失 |
| FR-07 | 断线恢复 | 玩家重连后继续查看最新房间状态 | 持久通信、事件补发、快照恢复 |

### 3.3 非功能需求与初始假设

以下数值已由用户确认保留为课程设计中的**暂定设计目标**。它们不是教师规定的硬性指标，也未经实现、压测或性能测试验证；最终报告必须明确标注为设计假设，不得写成已实现或已验证的性能承诺。

| 目标 | 暂定假设/目标 | 设计含义 |
|---|---|---|
| 房间规模 | 每房间 2–8 名成员（含主持人） | 以小型桌游协作为主，避免无必要的超大房间设计 |
| 初始系统规模 | 约 100 个活跃房间 | 用于讨论多房间分配，不代表已完成压力测试 |
| 实时性 | 同地域、网络正常时，从权威数据库提交到授权在线客户端收到更新的 P95 延迟目标不超过 300 ms | 需要定义测量环境和接收端计时方式；尚未验证 |
| 常规 API 延迟 | 服务端收到请求至返回响应的 P95 目标不超过 500 ms（不含地图文件传输） | 已确认的设计假设，尚未测试；若后续验证，需定义测试负载 |
| 恢复性 | 普通规模房间在网络恢复后，授权状态恢复目标不超过 5 秒 | 已确认的设计假设，尚未测试；依赖状态缺口、快照大小和网络条件 |
| 状态正确性 | 同一房间内已接受的共享操作有明确顺序；冲突不能静默覆盖新状态 | 由权威处理路径与冲突检查支撑 |
| 安全性 | 只有有权限的成员可以读取或修改相应内容 | 隐藏地图信息必须在服务端过滤 |
| 可扩展性 | 不同房间可分配给不同协作服务实例 | 扩展房间数量时不要求全系统单点串行处理 |

当前版本保留全部已确认数值。最终报告必须将它们标注为未经测试的设计假设/目标，不得写成已实现或已测试的性能承诺。

## 4. 概要架构与核心设计思路

### 4.1 逻辑组件

| 组件 | 主要职责 | 与分布式系统知识的联系 |
|---|---|---|
| 浏览器客户端 | 显示地图和标记、提交用户操作、处理服务端更新 | 客户端进程、瘦客户端、网络通信 |
| 接入层 | 接收管理请求与实时连接，完成身份校验和请求转发 | 客户端—服务器架构、协议分层 |
| 应用与房间协作服务 | 管理房间与权限，校验操作，并为房间内共享状态确定权威顺序 | 服务端进程、并发控制、同步 |
| 持久化存储 | 保存关键房间状态及恢复所需的历史信息 | 事务、复制、一致性与恢复 |
| 临时状态/通知组件（可选） | 辅助维护在线状态、路由信息或快速通知 | 缓存、发布订阅、瞬态通信 |
| 预置地图资源存储 | 保存系统提供的地图图片等静态资源；当前不包含用户上传流程 | 分层架构、资源命名与访问 |

以上是逻辑职责，不要求每一项都拆成独立微服务，也不在本阶段锁定所有中间件或部署产品。

### 4.2 一次协作操作的高层流程

以玩家移动角色标记为例：

1. 客户端向服务端提交“希望把标记移动到某位置”的操作。
2. 服务端检查用户身份、操作权限以及请求是否基于过期状态。
3. 服务端按该房间的权威顺序接受或拒绝操作，并保存需要恢复的关键结果。
4. 已接受的状态变化通知其他有权限的房间成员。
5. 如果客户端断线或漏收更新，重连后通过补发缺失事件或重新获取当前状态恢复。

报告应解释每一步对应的分布式问题及选择理由，不需要展开成完整 API 字段表、SQL 锁定顺序或代码伪实现。

### 4.3 核心方案取舍

- **客户端—服务器优于全 P2P 作为本项目的核心架构：** 服务端更容易统一检查权限、主持人规则和战争迷雾，也便于维护房间状态；代价是服务端成为关键依赖，因此必须讨论扩展与故障恢复。
- **管理请求与实时消息分工：** 房间创建、加入等操作适合请求—应答；持续状态更新适合双向实时通信。实时连接不等于消息已经持久化或一定送达。
- **按房间确定操作顺序：** 不同房间可并行处理；同一房间的共享状态需要一个可解释的权威顺序。物理时钟不能直接作为所有并发操作的最终裁决依据。
- **区分权威状态和临时信息：** 核心游戏状态需要明确的顺序和恢复依据；在线状态、光标等临时信息可以容忍短暂滞后。
- **以持久记录支撑恢复：** 不能只依赖在线广播。断线后重新验证权限，再补发可用更新或获取当前授权状态；无需在概要设计中规定精细游标和周期水位协议。
- **控制技术复杂度：** DHT/Chord、向量时钟、分布式互斥、Quorum、2PC/3PC 等按课件要求进行适用性比较；只有业务需求确实需要时，才把它们纳入核心设计。

- 参考文献按模板的数字角标方式组织，正文引用与文末条目一一对应。

## 7. 图表策略：少而有用

最终报告不需要把仓库中全部 10 张图都放进正文。建议正文优先保留以下 5 张，视篇幅再增加 1–2 张：

1. **总体逻辑架构图：** 展示客户端、接入层、房间协作服务和存储的职责关系。
2. **部署/房间分配图：** 展示多个房间如何分配给不同服务实例，帮助解释系统的扩展性。
3. **标记移动时序图：** 展示客户端请求、服务端校验、状态接受和房间成员收到更新的过程。
4. **并发操作示意图：** 用两名玩家同时移动同一标记的例子解释同步与操作排序。
5. **断线恢复流程图：** 展示重连后如何恢复状态，以及为什么不能只依赖实时广播。

可选图表：系统上下文图、战争迷雾权限图、核心实体关系图。若篇幅有限，实体关系图放附录或省略；租约/epoch 等细节较多的协调者故障切换图不作为正文必选图。
