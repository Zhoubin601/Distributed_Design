# 雾桌：多人实时协作在线虚拟桌游平台概要设计

> 文档版本：v0.2（概要设计基线）  
> 选题：B——多人实时协作的在线虚拟桌游平台（参考 Owlbear Rodeo）  
> 状态：设计规划材料，尚未实现或进行性能测试。  
> 理论依据：课堂课件《Introduction to Distributed System-by JieSong NEU》Chapter 1–8；最终报告格式以 raw/课程设计模板.docx 为准。  
> **深度边界：** 本文只描述系统需求、组件职责、核心协作过程和课程知识点的应用。接口字段、数据库字段、索引、租约算法及精细重试协议属于辅助材料，不作为概要设计正文主线。

## 1. 系统简介

雾桌是一种在线虚拟桌游平台。主持人与玩家可以使用不同设备加入同一房间，共同查看地图、移动角色标记、掷骰，并由主持人控制战争迷雾等可见性规则。

它属于分布式系统，不只是因为它使用了网络，而是因为多个独立客户端和服务端进程需要通过网络协作，共享房间状态；网络会延迟或中断，消息可能重复，服务进程也可能单独发生故障。因此，系统必须明确由谁决定操作结果、如何传播状态，以及出现故障后如何恢复。

### 1.1 核心需求

| 类别 | 需求 |
|---|---|
| 功能需求 | 创建/加入房间、地图与标记操作、掷骰、主持人权限控制、战争迷雾、实时状态更新 |
| 并发需求 | 多名玩家可能同时操作；系统需要对同一房间内的有效修改给出可解释的处理顺序 |
| 一致性需求 | 房间关键状态以服务端确认的结果为准；客户端短暂落后时能够重新同步 |
| 安全需求 | 服务端验证房间成员和操作权限；隐藏区域的信息不能通过更新或恢复流程泄露 |
| 容错需求 | 客户端断线、请求超时或服务进程故障时，系统不能把未确认的操作随意当作成功 |

以下数值已由用户确认保留为课程设计假设，并非课程规定的硬性指标，也未经实现、压测或性能测试验证：每房间最多 8 人、约 100 个活跃房间、同地域正常网络条件下从权威数据库提交到授权在线客户端收到更新的 P95 目标不超过 300 ms、常规 API 从服务端收到请求到返回响应的 P95 目标不超过 500 ms（不含地图文件传输）、网络恢复后普通规模房间的授权状态恢复目标不超过 5 秒。最终报告必须明确标注这些数值为未经测试的设计假设/目标。

## 2. 体系结构

### 2.1 技术需求

系统需要支持多个客户端同时接入、处理实时操作、保护不同玩家的可见范围，并把已经确认的关键状态持久保存。架构既要让不同房间能够并行工作，也要避免同一房间出现两个互相矛盾的权威结果。

### 2.2 概要设计

采用分层的客户端—服务器架构。客户端负责显示与提交操作意图；服务端验证身份、权限和规则，并维护房间的权威状态。逻辑上，同一房间在同一时刻只有一个权威处理路径，不同房间可以分配给不同实例并行处理。

~~~mermaid
flowchart LR
    C1["主持人浏览器"] <--> GW["接入层<br/>HTTPS / WebSocket"]
    C2["玩家浏览器"] <--> GW
    C3["其他玩家浏览器"] <--> GW
    GW <--> R["房间协作服务<br/>权限检查与操作排序"]
    R <--> DB[("持久化存储<br/>房间状态与恢复记录")]
    R --> GW
    GW --> C1
    GW --> C2
    GW --> C3
    GW -. "地图资源请求" .-> OBJ[("地图与静态资源存储")]
~~~

**图 1：系统总体架构。** 这是逻辑架构图，不要求每个组件都拆成独立微服务。若部署多个网关或服务实例，可以增加路由、缓存或消息通知设施，但它们属于部署扩展选择，不是核心设计成立的前提。

| 组件 | 主要职责 |
|---|---|
| 浏览器客户端 | 显示地图和标记，提交操作，展示服务端确认的结果 |
| 接入层 | 处理房间管理请求、维护实时连接、转发已认证的消息 |
| 房间协作服务 | 检查成员权限与游戏规则，确定房间内操作顺序，生成权威状态变化 |
| 持久化存储 | 保存房间关键状态及必要的操作记录，支持重连和服务恢复 |
| 预置地图资源存储 | 保存系统提供的地图图片等静态资源，不承担房间操作排序；当前不包含用户上传流程 |

### 2.3 架构取舍

与全 P2P 相比，客户端—服务器更容易统一执行主持人权限和战争迷雾规则，也更容易维护共享状态。代价是服务端成为关键依赖，因此需要考虑服务扩展与故障恢复。

本设计不要求所有逻辑组件各自部署，也不预先锁定特定消息中间件。课程报告应重点解释组件职责和选择理由，而不是列出一长串基础设施产品。

## 3. 进程

系统中的主要进程包括浏览器客户端、接入服务和房间协作服务。它们通过网络交换请求和状态更新，各自可能独立运行、延迟或失效。

同一房间的操作由一个权威处理路径按顺序判断和提交；不同房间之间没有必要共享同一条操作队列，可以并行处理。这种划分兼顾了同一房间状态的可解释性和多房间的扩展能力。

如果房间服务实例发生故障，接管实例必须先确认原有权威路径不再继续写入，并从持久化数据恢复已提交状态后再恢复服务。具体租约、任期或选举算法属于更深入的实现设计，本报告只说明这一安全前提与恢复边界。

## 4. 通信

### 4.1 技术需求

房间创建、加入和读取配置等操作适合请求—应答通信；角色移动、掷骰结果和房间状态更新需要及时传播，适合双向实时通信。实时消息不等于数据已经持久保存，也不意味着每个客户端一定收到消息。

### 4.2 概要设计

- HTTPS/REST 用于房间创建、加入、退出和读取配置等管理操作。
- WebSocket 用于实时操作请求、操作结果和房间状态更新。
- 客户端提交的是操作意图，而不是可以直接覆盖权威状态的整份地图。
- 服务端先检查权限和规则，再保存已接受的状态变化；只有确认提交后，才向客户端返回成功并传播更新。
- 推送内容由服务端按接收者权限生成。若客户端状态落后，可以请求重新同步；服务端补发可用的更新，或返回当前权限下的完整状态。

~~~mermaid
sequenceDiagram
    participant C as 玩家客户端
    participant G as 接入层
    participant R as 房间服务
    participant D as 持久化存储
    participant O as 其他有权查看的玩家

    C->>G: 提交移动标记请求
    G->>R: 转发已认证请求
    R->>R: 检查权限、规则与并发状态
    R->>D: 保存已接受的状态变化与操作结果
    D-->>R: 确认提交
    R-->>G: 返回权威操作结果
    G-->>C: 返回操作结果
    R-->>O: 传播权限过滤后的状态更新
~~~

**图 2：一次协作操作的主要流程。** 重点是请求先经过服务端判断，状态确认后再向其他成员传播，而不是依赖客户端时间或本地显示来决定最终结果。

## 5. 命名

命名和寻址解决的是不同问题：

| 名称 | 作用 |
|---|---|
| roomId | 稳定地标识一个桌游房间 |
| inviteCode | 帮助用户加入房间，不等于服务端网络地址 |
| operationId | 标识一次逻辑操作，用于识别重试 |
| 服务地址 | 表示客户端或服务之间实际建立网络连接的位置 |

客户端只需要使用稳定的房间标识与服务提供的访问入口，不需要自行推导房间当前部署在哪台机器。房间目录或路由服务可以把 roomId 映射到当前负责的服务实例。

DHT/Chord 等去中心化查找方案可以用于课程比较，但当前规模和需求没有要求自行实现覆盖网络。

## 6. 同步

### 6.1 同一房间的并发操作

例如，两名玩家几乎同时移动同一个标记。客户端的本地时间并不能可靠决定谁的操作应该生效。房间服务会依次检查操作与当前状态：先被接受并提交的修改成为新的权威状态；后续操作如果仍基于过期状态，就需要被拒绝或重新判断。

操作标识可以帮助系统识别同一次请求的重试，避免响应丢失后重复掷骰或重复推进状态。对象版本检查可用于发现过期修改，但它不等于房间内的事件顺序。

### 6.2 为什么不使用更复杂的协调机制

本系统的核心业务可以由房间服务为同一房间确定操作顺序，因此不需要让每个浏览器通过向量时钟合并同一份权威游戏状态，也不需要为每次移动都设计分布式互斥算法。

Lamport 时钟、向量时钟、分布式互斥和选举机制仍可用于比较，报告需要说明它们解决的问题及引入的复杂度，而不是把它们全部堆入实现。

## 7. 一致性与复制

房间状态、角色位置、回合信息和已确认的掷骰结果会影响游戏过程，因此必须以服务端确认的状态为准。客户端收到实时更新可能存在短暂延迟；如果错过更新，应通过重新同步回到服务端当前状态。

不同数据不必采用完全相同的一致性要求。例如，在线状态可以短暂滞后，而已确认的游戏操作必须具有明确结果。持久化存储负责保留权威状态及必要的恢复记录。

主备复制可以改善恢复能力或读取能力，但同步复制通常会增加写入等待，异步复制则可能在故障切换时丢失尚未复制的数据。Quorum 可以作为课件中的比较方案；如果没有定义副本数、读写条件和故障假设，本设计不声称采用 Quorum，也不承诺零数据丢失。

## 8. 容错与故障恢复

| 故障场景 | 概要处理方式 | 需要明确的边界 |
|---|---|---|
| 玩家断线 | 重新连接、重新验证权限，再补发可用更新或获取当前状态 | 断线期间无法保证实时可见 |
| 请求超时 | 使用同一操作标识查询或重试，避免重复副作用 | 超时不代表服务端一定没有提交 |
| 房间服务崩溃 | 暂停该房间写入，由有效接管路径恢复已提交状态后再服务 | 接管需要防止旧实例继续写入；本设计不声称该机制已经实现或测试 |
| 更新消息丢失 | 根据持久化状态重新同步，不把一次广播当作唯一记录 | 客户端可能暂时落后 |
| 持久化存储不可用 | 暂停无法安全确认的写操作，并向客户端返回可重试错误 | 数据恢复能力取决于实际备份与复制配置 |

如果一次操作涉及的状态和记录都在同一个数据库事务内完成，就不需要仅仅因为系统包含多个服务组件而引入 2PC/3PC。只有需要协调多个独立事务参与者的原子提交时，才有必要进一步讨论分布式提交协议。

## 9. 权限与战争迷雾

主持人和普通玩家的可见范围可能不同。服务端必须在状态更新和重新同步时都检查当前权限，只向玩家发送其有权查看的内容。不能只隐藏客户端界面上的元素，因为未经授权的数据一旦发送到浏览器，仍然可能被读取。

当玩家权限变化或退出房间后，服务端需要重新验证其成员资格，并拒绝不再授权的状态读取和更新请求。

## 11. 设计范围与限制

当前核心范围只包括主持人和普通玩家；观察者角色是否纳入仍待确认。地图资源已确定仅从预置地图中选择，不包含用户上传流程。系统设计聚焦常见网络故障和进程崩溃，不声称覆盖拜占庭容错、跨地域灾难恢复或无条件零数据丢失。

本项目的目标是用可解释的方案覆盖课程知识，而不是实现 CRDT/P2P、DHT/Chord、应用层 Quorum 或完整的协调者选举系统。

## 12. 设计结论

本设计以客户端—服务器架构承载实时桌游协作，以房间为单位确定共享状态的权威操作顺序，并通过持久化记录、权限检查和重新同步应对常见网络与进程故障。它将课程知识点与具体业务问题相联系，同时把超出概要设计范围的实现细节留作后续工作。
