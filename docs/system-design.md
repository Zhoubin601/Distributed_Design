## 1. 项目概述

### 1.1 设计背景

线下桌游通常需要实体地图、角色棋子、骰子和主持人。在线协作时，玩家可能使用不同设备和网络加入同一房间，因此系统需要解决共享状态同步、并发操作、权限控制、断线恢复和服务故障等问题。

本设计提出“雾桌”（MistTable）平台。玩家可以创建房间、邀请其他玩家、共同查看地图、移动角色标记、掷骰子和推进回合。主持人可以编辑地图并控制战争迷雾（Fog of War），决定每名玩家能看到哪些区域和标记。

本项目的重点不是堆叠复杂技术，而是把分布式系统课程中的体系结构、进程、通信、命名、同步、一致性与复制、容错机制应用到可解释的业务场景中。

### 1.2 设计目标

- 让同一房间的玩家看到一致且有明确顺序的权威游戏状态。
- 支持多个房间并行运行，避免所有操作都由单个全局服务串行处理。
- 在网络抖动、重复请求和客户端重连时，尽可能恢复到可验证的状态。
- 对战争迷雾、主持人操作和玩家操作实施服务端权限检查。
- 用可测量的指标描述服务目标，并明确这些指标仍需测试验证。

### 1.3 系统范围

| 范围 | 本设计包含的内容 |
|---|---|
| 房间管理 | 创建房间、加入/离开房间、成员与角色权限 |
| 桌面协作 | 地图加载、标记移动、地图编辑、房间内实时更新 |
| 游戏操作 | 服务端掷骰、回合推进、操作记录 |
| 可见性控制 | 主持人控制战争迷雾；服务端按玩家权限过滤状态 |
| 状态恢复 | 事件记录、状态快照、断线重连、重复请求去重 |
| 运行管理 | 房间服务分配、协调者租约、故障后的恢复流程 |

**本阶段不作为核心范围：** 语音/视频通话、内置支付、跨房间交易、复杂匹配系统、拜占庭容错，以及没有明确业务需求的去中心化 P2P 游戏状态合并。

### 1.4 设计假设与初始目标

以下数值是用于指导概要设计和后续测试的**初始设计目标**，不是已经测得的性能结果，也不是课程文件规定的指标。

| 项目 | 初始假设/目标 | 说明 |
|---|---|---|
| 单房间人数 | 2–8 人 | 以小型桌游房间为主要场景 |
| 初始并发规模 | 100 个活跃房间 | 作为后续压力测试的目标场景 |
| 同区域实时更新延迟 | p95 不高于 300 ms | 从服务端提交操作到在线成员收到更新；需定义测试环境 |
| 常规 API 延迟 | p95 不高于 500 ms | 在目标并发负载下测量 |
| 重连恢复时间 | 常见场景目标暂定不高于 5 s（与 plan.md 对齐，待确认） | 取决于事件缺口、快照大小和网络状况 |
| 网络假设 | 延迟、断连、消息丢失和重复投递都可能发生 | 不假设网络可靠或延迟为零 |
| 故障假设 | 重点处理非恶意的进程崩溃、网络故障和存储暂时不可用 | 不承诺拜占庭容错 |

## 2. 需求分析

### 2.1 功能需求

| 编号 | 需求 | 验收思路 |
|---|---|---|
| FR-01 | 用户可以创建房间并通过邀请码加入 | 未授权用户不能进入私有房间 |
| FR-02 | 房间成员可以看到被授权的地图和标记 | 不同权限玩家收到的可见状态符合权限规则 |
| FR-03 | 玩家可以请求移动自己有权操作的标记 | 越界、越权和过期版本操作被拒绝 |
| FR-04 | 玩家可以请求掷骰子和推进回合 | 随机结果由服务端产生，并记录到事件日志 |
| FR-05 | 房间状态变化可以实时推送给在线成员 | 成员收到按房间序号排序的更新 |
| FR-06 | 客户端断线后可以重新加入并恢复状态 | 支持事件补发；缺口过大时通过快照重同步 |
| FR-07 | 重试同一操作不会重复产生业务副作用 | 相同操作 ID 只产生一次权威结果 |
| FR-08 | 主持人可以调整战争迷雾与成员权限 | 服务端过滤不同玩家的地图投影和事件内容 |

### 2.2 非功能需求

| 编号 | 需求 | 设计措施 |
|---|---|---|
| NFR-01 一致性 | 同一房间的权威状态变更具有明确顺序 | 房间级单写入协调者、单调递增的房间序号、数据库事务 |
| NFR-02 可恢复性 | 短暂断线或服务进程崩溃后可恢复已提交状态 | 持久事件日志、周期快照、重连补发 |
| NFR-03 可扩展性 | 增加房间数量时可以增加房间服务实例 | 不同房间分配到不同实例，网关与房间服务可横向扩展 |
| NFR-04 安全性 | 用户只能读取和修改被授权的数据 | 服务端鉴权、权限校验、按用户过滤消息 |
| NFR-05 可观测性 | 能定位延迟、重复请求、恢复失败和房间服务故障 | 记录房间 ID、操作 ID、事件序号、协调者任期和耗时 |
| NFR-06 可维护性 | 各层职责明确，协议可扩展 | 分层架构、统一消息格式、稳定资源标识 |

## 3. 总体架构设计

### 3.1 架构选择

本系统采用**分层的客户端—服务器架构，并以房间为单位分配权威协调者**。

- 浏览器客户端负责界面交互、显示和发送操作意图；客户端不直接决定权威游戏结果。
- 接入网关负责身份校验、HTTP 请求和 WebSocket 连接。
- 房间服务负责校验游戏规则、权限和版本，并为本房间的操作确定顺序。
- PostgreSQL 保存权威业务数据、房间事件、操作去重记录、快照和协调者租约。
- Redis 可用于在线状态、路由缓存和跨网关即时通知，但不作为权威事件日志。
- 地图图片等较大的静态资源可以存放在对象存储中；对象存储故障不应直接改变已经提交的房间状态。

### 3.3 组件职责

| 组件 | 主要职责 | 不应承担的职责 |
|---|---|---|
| 浏览器客户端 | 显示地图、发送操作、保存最后收到的事件序号 | 不决定最终骰子结果，不自行绕过服务端权限检查 |
| HTTPS API | 房间创建、加入、读取配置、上传/获取资源授权 | 不代替房间服务处理所有实时状态竞争 |
| WebSocket 网关 | 维护连接、转发房间消息、发送授权后的事件 | 不将未经持久化确认的操作当作已提交结果 |
| 房间服务 | 权限和规则校验、并发控制、版本推进、事件提交 | 不把客户端时间戳当作权威顺序 |
| 事件发布器 | 将已提交事件通知到对应网关 | 不作为唯一事件存储 |
| PostgreSQL | 保存权威状态、事件序号、操作去重结果、快照与租约 | 不依赖内存状态作为唯一恢复依据 |
| Redis | 在线状态、路由缓存、低延迟通知 | 不作为唯一持久日志或唯一数据恢复来源 |
| 对象存储 | 保存地图图片等静态文件 | 不保存需要事务性排序的房间操作序列 |

## 4. 房间状态与消息协议

### 4.1 权威状态原则

房间状态由服务端维护。客户端发送的是“操作意图”，例如“将标记 T 移动到坐标 (x, y)”，而不是直接上传一份可以覆盖服务端状态的完整地图。

房间服务收到操作后，依次执行：

1. 验证登录身份、房间成员身份与操作权限。
2. 检查操作 ID 是否已处理；若已处理，返回之前的结果。
3. 检查房间协调者任期、操作版本和游戏规则。
4. 在一个数据库事务内更新权威状态、递增房间序号、写入事件和操作结果。
5. 事务提交成功后，才将事件交给发布流程。
6. 网关按接收者权限过滤事件，再推送给对应客户端。

### 4.2 操作消息格式示例

以下是逻辑协议示例，不是要求客户端直接访问数据库的格式。

~~~json
{
  "type": "MOVE_TOKEN",
  "roomId": "room-7f31",
  "operationId": "op-91ac",
  "expectedObjectVersion": 7,
  "payload": {
    "tokenId": "token-18",
    "targetX": 12,
    "targetY": 8
  }
}
~~~

字段说明：

| 字段 | 含义 |
|---|---|
| type | 操作类型，服务端按白名单解析 |
| roomId | 操作所属房间 |
| operationId | 本次逻辑操作的唯一 ID；重试必须复用同一个 ID |
| expectedObjectVersion | 客户端读取目标对象时观察到的版本，用于发现过期对象修改；不等于内部 roomSequence |
| payload | 操作参数；具体字段由操作类型决定 |

数据库中的 room_event.sequence 是内部 roomSequence，用于给整个房间的规范事件日志排序，不直接作为客户端可见流的连续序号。服务端完成权限过滤后，为当前授权视图流分配连续的 deliverySequence，并附带 viewVersion 与不透明 resumeCursor。客户端只根据同一 viewVersion 下的 deliverySequence 检测可见事件缺口；不能把内部 roomSequence 的跳号直接判定为消息丢失，因为其中可能包含该玩家无权查看的事件。

## 5. 核心交互流程

### 5.1 玩家移动标记

~~~mermaid
sequenceDiagram
    autonumber
    participant C as 玩家客户端
    participant W as WebSocket网关
    participant R as 房间服务
    participant D as PostgreSQL
    participant E as 事件发布器
    participant O as 其他房间成员

    C->>W: MOVE_TOKEN + operationId + expectedVersion
    W->>R: 转发已认证的操作
    R->>R: 检查成员权限、规则和操作去重
    R->>D: 开启事务并校验租约任期
    R->>D: 更新状态、递增序号、写事件与操作结果
    D-->>R: 事务提交成功
    R-->>W: 返回已提交结果
    R->>E: 通知发布已提交事件
    E-->>W: 推送房间事件
    W-->>C: 返回权威结果
    W-->>O: 推送经过权限过滤的更新
~~~

**图 3：标记移动的主要时序。** 关键点是先提交、后确认和发布。若数据库事务失败，服务端不能向客户端声称该操作已经成为权威状态。

### 5.2 并发操作如何排序

假设玩家 A 和玩家 B 几乎同时移动同一个标记：

- 两个客户端都发送操作，但客户端本地时间不决定胜负。
- 房间服务按本房间的处理顺序验证操作。
- 第一个通过校验并提交的操作推进目标对象 version，并为内部规范事件分配新的 roomSequence。
- 第二个操作若依赖旧版本，则被拒绝或要求客户端刷新后重新操作；若业务允许重新计算，则由服务端基于最新状态重新验证。
- 服务端产生的事件具有递增序号，所有有权查看该事件的客户端按此序号应用更新。

~~~mermaid
flowchart TD
    A["玩家 A 请求移动标记"]
    B["玩家 B 请求移动标记"]
    Q["房间级操作队列"]
    V["校验权限、规则和版本"]
    C{"操作是否有效？"}
    COMMIT["数据库事务提交<br/>对象 version +1；内部 roomSequence +1"]
    REJECT["拒绝并返回最新版本"]
    EVENT["按当前权限生成投影<br/>分配 deliverySequence"]

    A --> Q
    B --> Q
    Q --> V
    V --> C
    C -- 是 --> COMMIT
    C -- 否 --> REJECT
    COMMIT --> EVENT
~~~

**图 4：房间内并发控制。** 该设计用房间级单写入顺序解决核心状态竞争；不需要让每个浏览器通过向量时钟自行合并同一份权威游戏状态。

### 5.3 断线重连与状态恢复

客户端为当前授权视图维护两个值：

- `lastDeliverySequence`：已经连续应用的客户端可见事件序号。
- `resumeCursor`：服务端签发的不透明恢复游标，指向已经完成权限过滤与扫描的内部事件日志位置，并绑定 roomId、当前成员和 viewVersion。

数据库内部 `room_event.sequence`（内部 roomSequence）给房间的完整规范事件流排序。战争迷雾过滤后，某个玩家看不到其中一部分事件，因此客户端不得要求内部 roomSequence 连续，也不能把它直接暴露为可见事件序号。

恢复过程如下：

1. 客户端发送 roomId、resumeCursor、lastDeliverySequence 和 viewVersion。
2. 服务端重新验证成员身份和当前权限，从游标之后扫描持久事件，并按当前权限生成可见投影。
3. 可见事件按顺序使用连续的 deliverySequence；隐藏事件不生成该玩家可见的 ROOM_EVENT。
4. 若游标失效、权限版本发生变化或事件已超出保留范围，服务端发送当前权限下的新快照，并重置该视图的事件进度。
5. 服务端定期发送 SYNC_WATERMARK，报告当前授权视图的 latestDeliverySequence 和可安全推进到的 resumeCursor。若服务端序号高于客户端已应用序号，客户端立即请求补发；若二者相同，客户端可以推进游标，越过没有可见变化的内部事件。

即时通知只是让网关尽快检查新事件的提示。网关还应在心跳或周期性对账时扫描游标之后的持久事件，这样即使最后一条通知丢失、后续没有新事件，客户端也能发现自己落后。

~~~mermaid
flowchart TD
    START["连接并认证<br/>发送 resumeCursor、lastDeliverySequence、viewVersion"]
    AUTH["重新验证成员与当前可见权限"]
    CHECK["从游标扫描内部事件并生成授权投影"]
    VALID{"游标有效且 viewVersion 未变化？"}
    REPLAY["按 deliverySequence 连续补发可见事件"]
    SNAP["发送当前权限下的新快照<br/>重置视图事件进度"]
    WATERMARK["发送 SYNC_WATERMARK<br/>确认 latestDeliverySequence 与 resumeCursor"]
    GAP{"客户端 deliverySequence 是否落后？"}
    CATCHUP["继续补发并对账"]
    DONE["恢复完成"]

    START --> AUTH --> CHECK --> VALID
    VALID -- 是 --> REPLAY --> WATERMARK --> GAP
    VALID -- 否 --> SNAP --> REPLAY
    GAP -- 是 --> CATCHUP --> WATERMARK
    GAP -- 否 --> DONE
~~~

**图 5：断线恢复与可见事件流对账。** 快照、事件补发和水位确认都必须使用当前权限视图。具体对账频率、快照间隔和事件保留量仍待确认。

### 6.2 数据写入约束

| 数据 | 关键约束 | 目的 |
|---|---|---|
| ROOM.current_sequence | 同一房间单调递增 | 形成可比较的权威事件顺序 |
| ROOM_EVENT | UNIQUE(room_id, sequence) | 防止同一房间出现重复序号 |
| ROOM_OPERATION | UNIQUE(room_id, operation_id) | 对客户端重试去重 |
| ROOM_SNAPSHOT | 按 room_id、sequence 标识 | 记录某一事件序号对应的状态快照 |
| ROOM_LEASE | 保存 owner_instance、epoch、expires_at | 协调者切换后识别旧任期写入 |
| ROOM_MEMBER | UNIQUE(room_id, user_id) | 避免同一用户在同一房间重复登记 |

**关键事务边界：** 更新房间状态、推进序号、插入 room_event、保存操作去重结果，应在同一数据库事务内完成。若事务回滚，这些变化一起回滚。

当前数据库设计采用 room_event 表中的 publish_attempts、next_attempt_at 和 published_at 作为待通知重试元数据，发布器扫描尚未通知的持久事件；本方案暂不另设独立 outbox 表。Redis 通知只是唤醒/传播信号，不代表每个客户端已收到事件。在线连接还需根据 resumeCursor 做周期性对账，避免最后一次通知丢失后一直停留在旧状态。

## 7. 命名、定位与房间路由

### 7.1 命名规则

| 名称 | 示例 | 用途 | 是否等同于网络地址 |
|---|---|---|---|
| roomId | room-7f31 | 稳定标识房间 | 否 |
| mapId | map-a83c | 稳定标识地图 | 否 |
| tokenId | token-18 | 稳定标识角色标记 | 否 |
| operationId | op-91ac | 标识一次逻辑操作，用于去重 | 否 |
| 邀请码 | Q7M4KP | 方便人类输入；可设置过期与撤销 | 否 |
| ownerInstance | room-worker-2 | 当前协调者实例的逻辑标识 | 否 |
| 网络地址 | 内部服务地址或网关地址 | 实际建立连接或路由请求 | 是 |

资源 ID 不应直接编码当前服务器 IP。否则房间迁移或实例替换时，所有引用都需要改变。

### 7.2 房间服务定位

- 房间租约记录是协调者归属的权威依据。
- 网关可以缓存 roomId 到 ownerInstance 的映射以减少查询，但缓存过期或路由失败时必须重新解析。
- 如果房间被迁移或协调者更换，更新路由信息后，新操作必须通过新的任期校验。
- 对当前规模而言，数据库房间目录与服务注册通常比直接引入 Chord/DHT 更简单；DHT 可以作为更大规模去中心化命名方案的比较对象。

## 8. 同步、一致性与复制策略

### 8.1 不同数据采用不同的一致性保证

| 数据类型 | 权威来源 | 设计保证 | 原因 |
|---|---|---|---|
| 标记位置、回合状态、骰子结果 | 房间服务 + PostgreSQL | 房间内按序提交；提交后才视为权威结果 | 这些数据会直接影响游戏过程 |
| 房间事件日志 | PostgreSQL | 序号唯一、按序读取、可用于补发和恢复 | 支撑重连与审计 |
| 玩家在线状态 | Redis/连接状态 | 允许短暂滞后，使用心跳和超时更新 | 在线状态瞬时变化频繁 |
| 聊天输入状态、光标位置 | 实时通道 | 可允许丢失或短暂延迟，按业务需要决定是否持久化 | 通常不决定权威游戏状态 |
| 地图图片等静态资源 | 对象存储/CDN 缓存 | 以资源版本或缓存策略更新 | 不需要参与每次房间操作事务 |
| 战争迷雾可见范围 | 服务端权限与房间状态 | 每次读取/推送都按用户权限过滤 | 避免隐藏信息泄露 |

### 8.2 为什么不用客户端时间戳决定最终顺序

不同客户端的物理时钟可能存在偏差，消息的发送时间也不等于服务端接收和提交的顺序。课件中的 Lamport 逻辑时钟能够表达满足因果顺序的逻辑时间，向量时钟可以更精确地判断因果关系；但本系统的核心房间状态采用单写入协调者和递增序号已经足够明确。

因此，本设计将 Lamport/向量时钟作为课程理论与替代方案进行比较，而不把它们强行加入核心状态写入路径。

### 8.3 复制策略

初期设计由 PostgreSQL 作为权威持久化来源，使用数据库本身支持的备份与复制能力提高恢复能力。是否采用同步或异步复制，应根据写入延迟和可接受的数据丢失窗口进行选择。

- **同步复制的取舍：** 更容易把确认写入与副本确认联系起来，但写入延迟和可用性可能受副本状态影响。
- **异步复制的取舍：** 写入响应可能更快，但主库故障时，尚未复制的已确认数据是否丢失取决于具体配置与故障切换机制。
- **Quorum 的取舍：** 需要明确副本数、读写 quorum 和交集条件。没有这些参数，不能笼统地声称“使用多数派就一定不会丢数据”。
- **Redis Pub/Sub 的边界：** 只用于即时通知，不代替持久日志；通知遗漏后由网关扫描 PostgreSQL 持久事件，并通过授权视图的 deliverySequence 与周期性水位对账补齐。

## 9. 房间协调者租约与故障切换

### 9.1 为什么需要任期（epoch）

如果房间服务实例崩溃后由另一个实例接管，旧实例可能只是网络变慢，而不是真正退出。旧实例恢复后若仍继续写入，就可能形成两个实例同时修改同一房间的情况。

当前概要设计提议用持久化房间租约和单调递增的 epoch 作为旧协调者隔离机制。新协调者接管时获取更大的 epoch；每次权威写事务都必须在数据库事务内校验租约有效性、owner_instance 和 epoch。该机制目前是设计提案，并非已实现或已验证的高可用保证；租约时长、续期、数据库故障时的接管策略和恢复演练仍待确认。

~~~mermaid
sequenceDiagram
    autonumber
    participant A as 旧协调者 A
    participant D as 数据库租约
    participant B as 新协调者 B

    A->>D: 持有 epoch=7 的有效租约
    Note over A: A 崩溃或与数据库失联
    D-->>B: 租约过期后允许 B 申请接管
    B->>D: 获取新租约 epoch=8
    B->>D: 写入前校验 epoch=8
    D-->>B: 校验通过，允许提交
    A->>D: A 恢复，尝试用 epoch=7 写入
    D-->>A: 任期过期，拒绝写入
~~~

**图 7：租约与 fencing token 示意图。** 这要求租约校验真正进入权威写事务，不能只在应用启动时检查一次。广播也应在提交成功后进行；客户端还需按事件序号丢弃过期更新。

### 9.2 选举机制的适用范围

本设计优先用持久租约和单调任期标识来定义协调者切换。如果部署环境已有可靠的编排与服务发现机制，可以让它负责实例启动与健康检查，但仍要在数据写入处实施任期校验。

Bully 或环选举算法可用于课程方案比较；只有在系统要求节点自行协商选主、且没有合适的外部协调机制时，才有必要进一步设计具体选举协议。选举成功本身不等于旧主已被隔离。

## 10. 容错与恢复设计

### 10.1 故障场景表

| 故障场景 | 检测/判断 | 系统行为 | 数据风险与边界 |
|---|---|---|---|
| 玩家客户端断线 | WebSocket 关闭、心跳超时 | 清理/更新在线状态；允许重新连接和补发 | 临时在线状态可能短暂不准确 |
| 网关进程崩溃 | 连接断开、健康检查失败 | 客户端重连其他网关，按 resumeCursor 恢复授权视图 | 未提交操作不能被当作成功 |
| 房间服务崩溃 | 心跳/租约超时 | 新实例获取更高 epoch，从快照与事件恢复 | 恢复时间受租约期限、快照和事件数量影响 |
| 客户端重复提交 | operationId 重复 | 返回已记录结果，不重复执行副作用 | 需要唯一约束和事务性去重 |
| 数据库暂时不可用 | 事务失败或连接失败 | 暂停权威写入并向客户端返回可重试错误 | 不能在未提交时广播为成功 |
| Redis 不可用 | 缓存/通知错误 | 重新解析路由或重建在线状态；从数据库补事件 | 即时通知可能延迟，但持久事件不应只存在 Redis |
| 网络分区导致旧协调者失联 | 租约过期与 epoch 不匹配 | 新协调者接管；旧协调者写入被拒绝 | 必须校验每次写事务，避免脑裂写入 |
| 地图资源暂时不可用 | 对象存储请求失败 | 显示资源加载失败并重试；不篡改房间权威状态 | 资源可用性与房间事件一致性分开处理 |

### 10.2 恢复原则

1. **先恢复权威状态，再恢复实时显示。** 客户端不能因为本地还显示旧棋子位置就覆盖服务器数据。
2. **未确认不等于已提交。** 客户端超时后可以用同一个 operationId 重试，服务端通过去重记录返回原结果。
3. **恢复后检查可见流进度。** 客户端按 deliverySequence 去重并检测缺口；周期性 SYNC_WATERMARK 用于发现最后一条通知丢失的情况。内部 roomSequence 可能因权限过滤而跳号，不能直接用于客户端连续性判断。
4. **持久事件与即时通知分离。** 即时通知可以失败，但事件必须有可靠的持久来源。
5. **明确停服边界。** 数据库不可用时，宁可暂时拒绝权威状态修改，也不要接受无法可靠保存的操作并向玩家谎报成功。

### 10.3 为什么本设计不直接采用 2PC/3PC

课件 Chapter 8 讲解了两阶段提交（2PC）和三阶段提交（3PC）。本系统把单次房间状态修改、事件记录和操作去重放在同一个 PostgreSQL 事务中，因此该路径不需要额外的分布式提交协议。

如果未来一个业务操作必须同时提交到多个独立数据库或多个服务的本地事务中，就需要重新分析事务边界、参与者故障和协调者故障，再比较 2PC、3PC 或其他业务一致性方案。不能因为课件出现了 2PC/3PC 就直接假设系统需要它们。

## 11. 战争迷雾与权限安全

战争迷雾是本项目的业务特色，也是一项容易被忽略的分布式安全问题。

- 房间服务保存权威地图与完整可见性状态。
- 当前核心角色为主持人和普通玩家；观察者是否纳入范围仍待确认，暂不作为核心功能。
- 主持人可以编辑完整地图；普通玩家只能收到被授权的地图区域、标记和事件。
- 事件发布器不能直接把完整房间状态广播给所有客户端，而应先生成面向特定接收者的状态投影。
- 服务端每次处理移动、编辑地图和修改可见范围的操作时，都必须校验用户角色和对象权限。
- 邀请码只能用于加入流程，不能代替登录身份与房间权限检查。

~~~mermaid
flowchart TD
    EV["房间权威事件"]
    AUTH["读取成员身份与权限"]
    PROJ["按玩家生成可见状态投影"]
    HOST["主持人视图<br/>完整授权地图"]
    PLAYER["普通玩家视图<br/>仅可见区域"]
    OBS["可选：观察者视图<br/>是否纳入待确认"]

    EV --> AUTH --> PROJ
    PROJ --> HOST
    PROJ --> PLAYER
    PROJ -. "可选扩展" .-> OBS
~~~

**图 8：面向接收者的状态投影。** 前端隐藏元素只能改善界面体验，不能作为数据保密边界；不应授权的地图数据不能发送给该客户端。

## 14. 当前设计的限制与后续工作

1. 本文是概要设计草案，尚未实现数据库表、服务接口或故障切换代码。
2. 初始性能目标需要通过压测验证；若结果不满足目标，应根据瓶颈调整网关、房间分配、事件发布或数据库策略。
3. 协调者租约、fencing token、事件发布器和快照恢复需要在详细设计阶段明确事务隔离级别、索引、超时、重试与保留策略。
4. 房间事件对不同用户的可见性需要形成统一的服务端投影规则，并通过越权测试验证。
5. 如果后续需要跨数据库原子事务、去中心化状态合并或恶意节点容错，应以新增需求为依据重新选择协议，而不是默认扩展本版架构。

## 15. 设计结论

本设计选择“分层客户端—服务器架构 + 房间级权威协调者 + 持久事件日志与快照 + WebSocket 实时推送”的组合。

它的核心取舍是：以房间内明确的单写入顺序降低并发合并的复杂度，同时通过多个房间分配到不同服务实例实现横向扩展；用数据库事务保证权威状态与事件记录的一致提交；用事件序号、幂等操作 ID、租约任期和重连补发处理常见故障；通过服务端状态投影保护战争迷雾信息。

这些选择能够对应课程八章的主要知识点，并且每个机制都有明确的业务用途。后续应优先核对课堂课件术语、需求假设和报告结构；接口与数据表的细节仅作为支撑材料，是否继续展开取决于课程模板与教师要求。
