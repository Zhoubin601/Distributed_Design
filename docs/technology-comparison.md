# 技术方案比较与选型记录（v0.1）

> 当前阶段：课程设计规划与素材准备，不是实现说明，也不是最终报告正文。  
> 理论依据：raw/Introduction to Distributed System-by JieSong NEU.pdf 的 Chapter 1–8；章节与概念索引见 docs/knowledge-map.md。  
> 写作原则：课件概念用于建立比较维度；下表中的具体选择属于本项目的设计建议，不代表课件要求必须采用某个技术。

## 1. 选型标签说明

- **建议作为核心设计**：与当前需求直接相关，建议进入系统设计基线。
- **用于比较，不进入核心路径**：应在报告中解释适用条件与不采用原因，不需要实现。
- **待确认**：需要先确认需求、部署假设或数据库事务边界。
- **不覆盖**：本项目没有相应威胁或业务需求，不声称具备该能力。

## 2. 跨章节选型摘要

| 课件章节 | 需要回答的问题 | 当前建议 | 不作为核心的方案 | 报告中必须解释的代价或边界 |
|---|---|---|---|---|
| Chapter 1 导论 | 网络与事务失败如何影响共享状态？ | 明确网络延迟、断线、重复请求和部分失败；在单个 PostgreSQL 事务内提交房间状态、事件与幂等结果 | 无业务需要时不引入跨数据库分布式事务 | 数据库提交成功与网络消息送达是两件事 |
| Chapter 2 体系结构 | 谁维护同一房间的权威状态？ | 客户端—服务器架构；按房间分配权威协调者；逻辑上采用分层职责与事件通知 | 全 P2P、自组织覆盖网络 | 服务端较容易验证规则与权限，但会成为房间写入路径的关键依赖 |
| Chapter 3 进程 | 如何并发处理多个房间和多个连接？ | 不同房间并行处理；同一房间的权威写操作串行化或通过版本检查 | 客户端共同维护权威状态；动态代码迁移 | 单房间写入会有序列化开销，适合当前规模假设，不代表无限扩展 |
| Chapter 4 通信 | 管理请求、实时推送与恢复消息如何分工？ | REST 用于房间管理与查询；WebSocket 用于实时双向消息；持久事件记录支持补发 | 仅靠 WebSocket 内存广播；当前阶段引入 Kafka/RabbitMQ 等专用消息平台 | WebSocket 连接和发送成功都不等于事件已持久化或所有客户端已收到 |
| Chapter 5 命名 | 如何区分资源标识、邀请凭证与服务地址？ | 稳定 ID 标识用户、房间、地图、标记、操作和事件；邀请码仅用于加入；房间目录/服务发现负责定位 | 当前规模下自建 DHT/Chord 全网查找 | UUID 不等于网络地址；邀请码不是稳定主键，需限时、撤销或哈希存储 |
| Chapter 6 同步 | 并发操作的先后由谁决定？ | 服务端校验；数据库事务/锁与房间 sequence 定义权威提交顺序；对象 version 检测过期修改 | 让所有客户端通过 Lamport 互斥、Ricart–Agrawala 或令牌环共同决定每次移动 | 房间内串行化牺牲部分并发度，换取较清楚的规则和冲突处理 |
| Chapter 7 一致性与复制 | 不同数据需要什么一致性？如何恢复副本？ | 房间核心状态由权威写入路径提交；事件按序交付；在线状态允许短暂滞后；快照加事件日志用于恢复 | 应用层自行实现 Quorum；声称所有客户端任何时刻完全一致 | 数据库主备模式、同步/异步复制和 RPO/RTO 尚未确定，不能承诺零数据丢失 |
| Chapter 8 容错 | 崩溃、重试、消息丢失和协调者切换如何处理？ | 稳定 operationId 幂等；事件持久化、按序补发与快照恢复；协调者任期隔离作为候选设计 | 在单数据库事务范围内使用 2PC/3PC；未建模恶意节点却声称拜占庭容错 | 自动接管需定义租约获取、过期判断、写入 fencing 与数据库可用性边界 |

## 3. Chapter 1：事务与系统边界

| 方案 | 适用场景 | 对本项目的判断 |
|---|---|---|
| 单个数据库本地事务 | 一次操作所需更新都在同一个数据库内 | **建议作为核心设计。** 将房间状态、room sequence、room_event 与 room_operation 结果一起提交，避免状态已变而事件/幂等记录缺失 |
| 分布式事务（2PC/3PC） | 一次业务操作必须原子地提交到多个独立事务参与者 | **用于比较，不进入当前核心路径。** 当前设计将权威状态与事件放在同一 PostgreSQL 事务中；只有未来跨独立数据库的原子提交成为硬需求时再重新评估 |
| 仅先发送消息，再异步保存状态 | 对短暂丢失可容忍、消息不是权威事实的通知 | 不适用于标记位置、掷骰结果、回合状态等权威游戏状态 |

报告要点：ACID 事务只能保证数据库事务范围内的原子性与一致性，不能自动保证 WebSocket 消息必达。

## 4. Chapter 2：体系结构

| 方案 | 优点 | 代价/风险 | 当前判断 |
|---|---|---|---|
| 客户端—服务器（C/S） | 权限、规则、隐藏地图信息和权威状态集中校验；便于记录操作与恢复 | 服务端是关键依赖；需要扩展和故障恢复设计 | **建议采用** |
| 对等结构（P2P） | 部分计算和数据可由节点分担，降低单一服务端的中心程度 | 节点身份、权限、防作弊、状态冲突、节点离线和恶意行为更难处理 | **比较后不采用为核心架构** |
| 分层架构 | 接入、业务规则、持久化和资源存储职责清楚，便于独立演进 | 层间调用可能增加延迟与部署复杂度 | **建议采用职责分层** |
| 事件驱动 | 状态提交后可通知多个网关/成员，降低直接耦合 | 通知会重复、延迟或丢失；必须保留权威事件来源 | **仅用于事件传播，不替代事务和持久化** |

核心解释：每房间一个权威写入顺序，并不等于整个系统只有一个服务实例。不同房间可以由不同房间服务实例处理。

## 5. Chapter 3：进程与客户端职责

| 方案 | 做法 | 当前判断 |
|---|---|---|
| 瘦客户端/服务端权威 | 客户端负责交互和非权威预览；服务端验证权限、规则和版本 | **建议采用**，避免客户端伪造掷骰结果或绕过迷雾权限 |
| 胖客户端权威 | 客户端本地决定最终共享状态，再尝试同步给其他人 | 不适合权威游戏状态；可以用于拖动预览等非权威 UI |
| 多房间并行、单房间有序 | 不同房间可并行处理；同一房间的写入通过房间队列或数据库事务序列化 | **建议采用** |
| 动态代码迁移 | 将运行中的代码/执行状态迁移到其他机器 | 本业务没有明确需求，**不进入核心设计** |

## 6. Chapter 4：通信机制

| 方案 | 主要语义 | 优点 | 风险/限制 | 当前判断 |
|---|---|---|---|---|
| HTTPS/REST 请求—应答 | 一次请求对应一次响应，适合管理与查询 | 接口清晰，易于验证与调试 | 不适合高频双向推送 | 创建/加入房间、读取元数据等 |
| WebSocket | 建立双向连接，适合持续实时更新 | 延迟较低，服务端可主动推送 | 断线后连接状态消失；应用层仍需确认、去重和恢复 | 实时协作通道 |
| 瞬态通信 | 接收者不在线时，消息可能无法保留给之后读取 | 简单、延迟低 | 不适合作为唯一的恢复依据 | 可用于在线状态、临时提示或通知信号 |
| 持久通信/持久事件记录 | 消息或事件在接收者离线后仍有可恢复来源 | 支持补发和审计 | 需要存储、保留策略和清理机制 | 权威房间事件使用持久记录 |
| Redis Pub/Sub 即时通知 | 发布时通知当前订阅者，不作为事件历史 | 实现简单、通知快 | 订阅者断线时通知可能丢失 | 可作为提示信号，不是权威日志 |
| 专用消息队列 | 提供更丰富的缓冲、消费与重试能力，具体语义取决于产品配置 | 适合更大规模或多消费者系统 | 增加部署、监控、运维与消息一致性边界 | 当前规模暂不引入；持久事件表加发布器足以作为设计起点 |

重要流程：先提交数据库事务，再尝试发布通知。通知失败时，通过持久事件记录重试或在客户端重连时补发。若采用 outbox，必须明确 outbox 记录如何与业务状态在同一事务中提交。

## 7. Chapter 5：命名与服务定位

| 概念/方案 | 作用 | 本项目规则 |
|---|---|---|
| 稳定标识符（UUID 等） | 标识一个业务实体或操作 | userId、roomId、mapId、tokenId、operationId、eventId 各自有明确含义 |
| 邀请码 | 让用户加入房间的可分享凭证 | 不当作 roomId；可过期/撤销；数据库只保存邀请码哈希，避免日志泄露明文 |
| 网络地址 | 定位当前网关或服务实例 | 地址可能变化，不作为业务实体的永久身份 |
| 目录/服务发现 | 由 roomId 找到当前处理实例或路由信息 | 当前规模优先使用房间路由服务与缓存；缓存失效时需有权威重新解析路径 |
| DHT/Chord | 去中心化节点查找与结构化覆盖网络 | **用于课程比较，不作为核心实现**；需要维护路由表、节点加入退出和查找容错，超出当前必要复杂度 |
| DNS/层次化命名 | 解析服务域名或层次化资源名称 | 可用于部署服务的网络寻址，但不替代房间级授权和业务 ID |

## 8. Chapter 6：同步与并发控制

| 方案 | 如何排序/互斥 | 优点 | 代价/边界 | 当前判断 |
|---|---|---|---|---|
| 物理时钟/NTP | 同步不同机器的物理时间 | 有利于日志时间和运维观察 | 时钟有偏差；时间戳不能直接证明并发操作的权威先后 | 用于时间展示/诊断，不作为最终提交顺序 |
| Lamport 逻辑时钟 | 依据消息因果关系递增逻辑时间 | 可建立满足因果关系的逻辑顺序 | 无法单独识别所有并发关系；仍需确定相同时间戳的破同序规则 | 作为课程概念比较；当前不替代房间权威序号 |
| 向量时钟 | 用多个逻辑计数器更精细地判断因果关系与并发 | 能识别某些并发更新 | 元数据随参与者数量增长；对本项目单写入权威状态偏复杂 | 不作为核心状态排序机制 |
| 中心化互斥/房间协调者 | 由单一权威路径串行批准操作 | 规则清楚，容易拒绝冲突与越权操作 | 单房间吞吐受串行路径限制，协调者故障需恢复 | **建议作为核心方案** |
| Lamport/Ricart–Agrawala 分布式互斥 | 多个节点通过消息和请求队列协调临界区访问 | 不依赖单一互斥管理者的简单模型 | 需要多轮消息、节点状态和故障处理；节点失联会增加复杂度 | 用于比较，不用于每次标记移动 |
| 令牌环互斥 | 持有令牌者才能进入临界区 | 互斥规则直观 | 令牌丢失/重复、节点加入退出和环恢复需要额外机制 | 不作为核心方案 |
| Bully/环选举 | 节点故障时通过选举产生协调者 | 适用于满足相应假设的选举场景 | 需定义成员视图、超时、网络分区与旧主隔离 | 作为选举算法比较；当前拟用租约与 epoch 表达写入隔离，具体接管协议待细化 |

对象 version 与房间 sequence 不可混用：version 检查一个对象是否过期；sequence 给房间内已提交事件排序。

## 9. Chapter 7：一致性与复制

| 方案/模型 | 适用点 | 本项目的选择或边界 |
|---|---|---|
| 顺序一致性/权威排序 | 多人修改共享房间状态，需要所有已提交变更具有可解释的顺序 | 房间核心写入由权威路径提交并分配 sequence；客户端接收期间可能暂时落后 |
| 因果一致性 | 需要保留操作之间的因果先后 | 事件 sequence 提供房间内提交顺序；若未来有离线多主编辑，再重新评估是否需要更丰富的因果元数据 |
| 最终一致性 | 非权威数据允许短暂不同步并最终收敛 | 在线状态、光标等临时信息可接受短暂滞后；不能把它作为隐藏信息授权或核心状态冲突解决的替代品 |
| 客户中心一致性 | 从同一客户端视角，保证读写历史可解释 | 使用操作结果、operationId 去重、lastSequence 补发和快照恢复，支持可恢复的读自身写体验 |
| Primary-Backup/主备 | 主节点负责写入，备份副本用于恢复或接管 | 可作为数据库部署层的候选；复制是同步还是异步、确认条件与 RPO/RTO 仍待确认 |
| Quorum | 通过读写副本集合与交集条件设计可用性/一致性 | 需要明确 N、R、W 和故障假设；当前不在应用层自行实现 Quorum |
| Local-Write | 由各副本本地接受写入，再按协议传播/协调 | 多个客户端直接写权威状态会加重冲突与合并逻辑；当前不采用为核心路径 |
| 快照 + 事件日志 | 快照恢复较早状态，随后重放之后的事件 | **建议采用**，需定义快照序号、保留范围与不兼容版本处理 |

注意：数据库复制模式尚未决定。最终报告应写成“候选部署策略及取舍”，不要在未配置和测试前声称主备切换、同步复制或零数据丢失已经得到保证。

## 10. Chapter 8：容错与恢复

| 故障/机制 | 建议处理 | 不能夸大的保证 |
|---|---|---|
| 客户端断线 | 重连后重新认证并检查房间权限；从 lastSequence 补发或发送快照 | 不保证每条 WebSocket 通知都在原连接上送达 |
| 请求超时但服务端可能已提交 | 使用相同 operationId 重试或查询原结果 | 超时本身不能证明操作失败 |
| 重复请求 | 对同一 roomId + operationId 记录请求摘要与原结果 | 同一 ID 携带不同请求内容应报协议冲突，不可重复执行 |
| 发布通知失败 | 保留已提交事件并由发布器重试；客户端可补发 | Redis Pub/Sub 不能充当唯一的持久事件来源 |
| 房间协调者崩溃 | 候选流程为获取新租约/epoch、恢复状态、再开放写入 | 需要在权威写事务中验证 epoch；具体租约续期、超时和数据库故障边界仍待细化 |
| 数据库故障 | 不把未确认事务报告为成功；恢复能力依赖备份/复制配置 | 未定义复制和备份策略前不能声称零 RPO 或固定恢复时间 |
| 恶意/拜占庭节点 | 本项目先按非恶意崩溃、网络中断与消息丢失建模，并做认证和权限校验 | 不声称实现拜占庭容错协议 |
| 2PC/3PC | 当事务必须跨多个独立事务参与者时再分析 | 当前单 PostgreSQL 事务范围内不需要额外引入 |

## 11. 建议锁定的设计基线

### 建议作为核心设计

1. 浏览器客户端—服务器架构，按职责分层。
2. REST 负责房间管理和查询，WebSocket 负责实时协作消息。
3. 每个房间只有一个权威写入顺序；不同房间可以并行分配给不同实例。
4. PostgreSQL 保存权威状态、操作去重结果、事件日志、快照和租约记录。
5. 通过对象 version 检查过期写入，通过 room sequence 排列已提交事件。
6. 通过 operationId 幂等重试，避免重复掷骰或重复推进状态。
7. 使用持久事件与快照支持断线恢复；按当前成员权限生成客户端可见投影。
8. Redis 只用于在线状态、路由缓存和即时通知，不作为唯一权威事实来源。

### 仅用于课程比较，不纳入核心路径

- 全 P2P 架构。
- DHT/Chord 作为房间发现的基础设施。
- 每次移动操作都使用 Lamport/Ricart–Agrawala 或令牌环分布式互斥。
- 应用层自行实现 Quorum。
- 在单数据库事务内使用 2PC/3PC。
- 未有需求支撑的拜占庭容错。
- 动态代码迁移。

### 仍待确认或细化

- 每房间人数、延迟与恢复时间目标是否采用。
- 地图只选择已有资源还是允许上传。
- outbox 的具体表示：独立表，还是为持久事件表增加待发布状态与重试信息。
- 房间租约的获取/续期、过期判定和 epoch 校验事务。
- PostgreSQL 备份与主备复制模式、允许的数据丢失窗口和恢复目标。
- 是否需要观察者角色。
- 在线状态、聊天与光标是否纳入核心需求。
